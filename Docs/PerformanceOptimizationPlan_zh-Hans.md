# 启动加载与坐标识别优化实施计划

本文给出 `IMao-Core` 启动资源加载和游戏画面左下角坐标识别的实施计划。
计划以可测量、可回退和不改变现有地图定位语义为原则；地图点位数据、新地区坐标
换算和 WinUI 界面重做不在本轮范围内。

## 1. 现状基线

### 1.1 启动资源

- `Assets/FeaturesDatas/Map_features.yml` 实际为 OpenCV XML，大小为
  459.71 MiB。
- 文件包含 247,389 个关键点和 `247389 x 128` 个 `float` 描述子；描述子
  的原始二进制数据为 126,663,168 字节。
- 当前参考机器顺序读取整个 XML 约需 0.23 秒，但 OpenCV 打开、解析并取出数据
  合计约需 18.2 秒，瓶颈是十进制浮点文本解析。
- 每次点击“开始”都会创建新的 `App` 并加载特征；停止时又会释放特征，因此同一
  进程内再次开始仍需重新解析。
- 首帧截图调用后还有固定两秒等待；它不能直接删除，必须改成真正的首帧完成信号。

### 1.2 坐标识别

- 1920 x 1080 下的实际坐标裁剪约为 159 x 39，但当前会先放到 1000 x 500
  黑底，再以最近邻方式放大。
- 每次识别均执行文本检测、方向分类和通用中文识别，未利用坐标固定、单行、水平、
  字符集很小的特点。
- 两次现有诊断会话共记录 63 次 OCR 尝试：37 次未检测到文本，17 次通过 OCR
  格式检查，最终 15 次通过地图特征验证并完成定位。
- 已观察到 `-6901` 被高置信度识别为 `6901`，以及分隔符缺失、无关中文和英文
  输出。一次小地图连续匹配失败也会过早触发昂贵的 OCR 恢复。

所有性能数据必须在 Release 构建上重新记录；以上数据用于确定问题方向，不作为
最终验收结果。

## 2. 交付目标

在同一台参考机器、Release x64、资源位于本地 SSD 的条件下，目标如下：

| 指标 | 目标 |
| --- | --- |
| 基础地图特征冷加载 P95 | 不超过 2 秒 |
| 同进程停止后再次开始的资源等待 P95 | 不超过 200 毫秒 |
| 特征加载阶段新增峰值内存 | 不超过 180 MiB |
| 可见且稳定的坐标 ROI 识别成功率 | 不低于 95% |
| 坐标识别 CPU 推理 P95 | 不超过 100 毫秒 |
| 进入恢复状态后重新锁定坐标 P95 | 不超过 500 毫秒 |
| 地图切换、过场和坐标不可见时启动 OCR | 0 次 |
| 回归样本中的错误坐标最终被接受 | 0 次 |

若通用 PP-OCRv5 识别器直读无法达到识别指标，再进入数字专用模型阶段；该阶段不是
首轮交付的前置条件。

## 3. 总体设计

运行时拆成两个独立、只读为主的服务：

```text
DLL_API / App
  |-- RuntimeFeatureRepository
  |     |-- 二进制特征加载器
  |     |-- XML 开发回退
  |     `-- 进程级只读缓存
  |
  `-- CoordinateRecognitionService
        |-- 状态门控与帧版本
        |-- 紧凑 ROI 预处理
        |-- 识别器直读
        |-- 候选解析与纠错
        `-- 时序、场景和地图特征验证
```

`App` 不再拥有和反复销毁基础地图特征，而是持有仓库返回的只读共享引用。坐标识别
不再直接修改全局定位状态，而是返回带置信度、来源和验证信息的候选结果，由状态机
决定是否提交。

## 4. 分阶段实施

### 阶段 0：基准、诊断和回归样本

1. 为下列阶段增加 `steady_clock` 毫秒计时：
   - 特征文件打开、校验、读取、构造 OpenCV 数据；
   - OCR 初始化和预热；
   - ROI 裁剪、预处理、检测、识别、解析、地图验证；
   - 首帧等待和最终可用时间。
2. 日志记录构建类型、资源格式版本、文件大小、关键点数、描述子形状、输入分辨率、
   OCR 状态和帧版本。
3. 从现有 `x64/Debug/Diagnostics` 中整理只包含左下角坐标条的回归样本，并记录预期
   文本、是否可见、是否允许提交和对应场景。
4. 首轮至少覆盖 100 张样本；游戏内验证后扩展到不少于 500 张，覆盖：
   - 1600 x 900、1920 x 1080、2560 x 1440；
   - 深色、浅色、植被、角色服装和高亮背景；
   - 正负号、四位数、坐标移动、静止和传送；
   - 地图打开/关闭、过场和坐标不可见帧。
5. 增加离线测试入口，输出 JSON 或 TSV 汇总，后续每一阶段使用相同样本比较。

验收：能一条命令生成启动和 OCR 基线报告，失败样本可从报告定位到具体图片与阶段。

### 阶段 1：二进制特征格式和加载器

1. 定义版本化的小端二进制格式，文件头至少包含：
   - 魔数、格式版本和字节序标记；
   - 关键点数量；
   - 描述子行数、列数、OpenCV 类型和数据长度；
   - 源 XML SHA-256 或资源版本；
   - 负载校验值。
2. 关键点逐字段序列化 `x`、`y`、`size`、`angle`、`response`、`octave`、
   `class_id`，不直接写入可能随编译器变化的 `cv::KeyPoint` 内存布局。
3. 描述子保证连续后按原始字节写入。加载前检查所有数量、乘法溢出、文件长度、
   类型和校验值，再一次性预分配目标容器。
4. 新增离线转换工具。工具读取 XML 后先写临时文件，重新读取并比较关键点和描述子，
   全部通过后才原子替换目标文件。
5. 运行时优先读取二进制文件。开发构建允许在二进制缺失时回退到 XML并记录日志；
   发布验证要求二进制存在且正确，不允许静默承担 18 秒 XML 解析。
6. 首轮只转换基础 `Map_features`。图标特征和可选地区特征包保持兼容，随后复用同一
   格式逐步迁移。
7. 将二进制资源加入 Git LFS、构建复制、发布清单和 SHA-256 归档。

验收：转换前后关键点各字段和描述子逐项一致；截断、错误版本、错误类型、错误校验值
均安全失败；冷加载 P95 达标。

### 阶段 2：进程级特征缓存和首帧就绪

1. 新增 `RuntimeFeatureRepository`，使用一次初始化或共享 future 保证并发请求只加载
   一份资源。
2. 在 DLL 初始化后后台预加载基础地图特征和 OCR 模型；点击“开始”只等待尚未完成
   的部分，并向现有通知系统报告阶段。
3. `App` 持有 `shared_ptr<const ImageFeatureData>` 或等价只读句柄。停止覆盖层时只停止
   线程和清理会话数据，不释放进程级基础特征；退出进程时统一销毁。
4. 可选地区特征与基础特征只合并一次。避免每次新建 `App` 时重复追加或复制。
5. 把 `FeatureFilter::FilterNearKeypoints` 的关键点参数改为常量引用，消除每次查询
   复制整个关键点数组的问题。
6. 用实际首帧完成事件替换固定两秒等待：
   - BitBlt 成功返回图像后立即继续；
   - Windows Graphics Capture 等待首帧事件并设置有限超时；
   - 超时后给出可重试错误，不用固定休眠掩盖异步状态。
7. 对开始、停止、再次开始和进程退出进行线程安全检查，防止缓存初始化与退出并发
   引发悬空引用。

验收：同一进程连续开始/停止 20 次只记录一次基础特征加载；重复开始资源等待 P95
达标；两种截图方式都不依赖固定休眠。

### 阶段 3：紧凑 ROI 和识别器直读

1. 将坐标 ROI 配置从裸坐标改为带基准分辨率和边界检查的结构；裁剪结果必须限制在
   快照范围内。首轮明确支持三种 16:9 分辨率，非 16:9 输入先安全拒绝并记录，避免
   错位识别被提交。
2. 新增坐标专用预处理函数，不再调用 1000 x 500 黑底的通用
   `centerAndScaleImage`：
   - 紧凑裁剪并去除无关上下边缘；
   - 灰度和局部对比度增强；
   - 使用白顶帽或自适应阈值抑制缓慢变化的游戏背景；
   - 按比例缩放到约 48 像素高并增加少量边距；
   - 使用三次或 Lanczos 插值。
3. 保留两路低成本输入：增强后的原色/灰度图和二值图。两路结果统一进入候选评分，
   只要单路满足验收即可，不要求两路都成功。
4. 对固定单行 ROI 关闭文本检测和方向分类，调用识别器直读；必要时在 PaddleOCR
   封装内暴露 `RecognizeOnly`，避免依赖不明确的组合参数行为。
5. 在模型初始化完成后执行一次小尺寸预热，首次真实坐标不再承担图优化和内存分配
   的全部延迟。
6. Release CPU 配置中验证 MKL-DNN 和合理的线程数；线程数通过基准选择，不硬编码为
   机器逻辑核心总数。

验收：离线样本中不再出现因检测框缺失导致的大量 `count=0`；单次推理 P95 达标；
输入图像中不再包含大面积无效黑边。

### 阶段 4：候选解析、时序融合和地图验证

1. 解析阶段直接处理 ASCII/UTF-8，不再为数字坐标转换到 GBK。
2. 先规范化 Unicode 负号、全角标点和常见逗号/句点混淆，再按坐标语法解析三个
   有符号整数。
3. 对缺失负号、逗号被识别为负号、分隔符缺失等情况生成数量受限的候选，不在解析
   阶段直接决定唯一答案。每个候选保留：
   - 原始文本与模型置信度；
   - 使用了哪些修正规则；
   - 与上一可信坐标的距离；
   - 场景和地图特征验证分数。
4. 新增定位状态机：
   - `Uninitialized`：首次锁定；
   - `Tracking`：小地图连续定位正常；
   - `Suspect`：少量连续匹配失败，仍保留上一可信坐标；
   - `Recovering`：稳定小地图画面上启动 OCR；
   - `Hidden`：地图、过场或坐标不可见，不启动 OCR。
5. 一次连续匹配失败只进入 `Suspect`；连续 2 至 3 帧失败后才恢复。具体阈值用回归
   数据确定。
6. 使用帧编号或状态代数标识 OCR 请求。识别完成时若画面已经切换，丢弃陈旧结果。
   后台只保留最新待识别帧，避免失败期间堆积任务。
7. 按上一可信场景优先验证候选。若高置信 OCR 的原坐标没有地图特征，立即尝试有限
   的符号和分隔符候选，不重新执行模型推理。
8. 提交策略：
   - 单帧候选只有通过地图特征验证才可立即提交；或
   - 两个相邻稳定帧结果一致，并满足移动速度/距离约束后提交；
   - 传送或切换场景时显式进入允许大跳变的恢复分支。
9. 旧的完整检测流程保留为有频率限制的临时回退，并由运行时开关控制；待新流程在
   游戏内验证稳定后移除。

验收：现有高置信错误正号样本不会被直接接受；地图切换产生的陈旧 OCR 不改变定位；
回归样本成功率、恢复时间和零错误接受指标达标。

### 阶段 5：集成验证和发布

1. 自动测试：
   - 二进制格式往返、版本、截断、校验、数量溢出和 XML 回退；
   - 坐标规范化、语法、候选生成、距离限制和状态转换；
   - 所有坐标截图的离线识别与提交判断；
   - 连续开始/停止和初始化并发压力测试。
2. 游戏内矩阵：
   - 三种支持分辨率；
   - BitBlt 和 Windows Graphics Capture；
   - 静止、持续移动、快速传送、进入新场景；
   - 打开/关闭地图、切出窗口、过场和 UI 遮挡；
   - 冷启动、同进程重复开始和完整进程重启。
3. 每次运行生成汇总：加载 P50/P95、OCR P50/P95、恢复耗时、OCR 调用次数、候选
   修正次数、地图否决次数和最终错误接受次数。
4. 更新构建文档、发行资源清单和故障排查说明。诊断模式保留原始紧凑 ROI、预处理
   结果和候选评分，但继续遵守现有图片数量和保存频率限制。
5. 发布前以旧 XML 和旧 OCR 开关完成一次对照运行；确认回退路径有效后再默认启用
   新实现。

验收：自动测试全部通过，游戏内矩阵无阻塞问题，第二节的所有强制指标达标。

## 6. 变更批次与依赖

建议按以下独立批次提交，每一批都保持可构建：

1. 毫秒级诊断、基准脚本和首批 OCR 回归样本；
2. 二进制格式、转换工具和格式单元测试；
3. 运行时二进制加载、XML 回退和发布复制；
4. 进程级特征缓存、常量引用和首帧完成事件；
5. 紧凑 ROI、双路预处理、识别器直读和模型预热；
6. 候选解析、状态机、时序/地图验证和陈旧任务取消；
7. 性能回归、游戏内矩阵、默认开关切换和发布文档。

批次 2 至 4 与批次 5 至 6 在完成批次 1 后可以独立开发，但最终必须在批次 7 进行
组合压力测试。

## 7. 风险与回退

| 风险 | 控制措施 | 回退 |
| --- | --- | --- |
| 二进制格式与编译器/OpenCV 版本耦合 | 固定字段格式、版本、长度和校验，不写结构体原始布局 | 开发模式回退 XML |
| 缓存导致内存常驻 | 数据只保留一份并记录峰值，App 只持有共享只读引用 | 运行时关闭预加载、恢复按需加载 |
| 后台初始化与停止并发 | 单次初始化 future、不可变发布、退出时明确 join | 关闭后台预加载，开始时同步等待 |
| 识别器直读对部分背景不稳 | 双路预处理、离线样本、地图验证 | 限频调用旧完整 OCR |
| 自动修正产生错误坐标 | 候选数量受限，必须经过时序或地图验证 | 关闭对应修正规则 |
| 画面切换后旧 OCR 回写 | 帧版本和状态代数，结果提交前复核 | 禁用异步识别、同步处理最新帧 |

## 8. 后续可选优化

只有首轮指标仍未达到时才进入以下工作：

1. 使用 `0123456789-+,.` 小字符集训练数字坐标专用 CTC 模型，并以同一回归集与
   PP-OCRv5 直读进行对照。
2. 将地图特征按场景和空间网格分片，首次只加载当前坐标附近网格并预取相邻区域。
3. 在二进制读取仍占明显比例时评估内存映射描述子；在此之前不引入映射生命周期
   和文件锁复杂度。
4. 为非 16:9 和自定义 UI 缩放增加基于 UI 锚点的 ROI 定位。

## 10. 完成定义

只有同时满足以下条件，本轮优化才算完成：

- 二进制资源可重复生成、可验证、可发布且加载指标达标；
- 同进程重复开始不重新加载基础地图特征；
- 固定两秒等待已由真实首帧完成机制替代；
- OCR 不再处理 1000 x 500 黑底，也不在固定单行场景执行检测和方向分类；
- 坐标提交必须经过状态、时序或地图特征验证，陈旧结果不能回写；
- 自动回归和游戏内验证矩阵通过，所有强制指标有机器可读报告；
- 新旧实现均有明确开关和经过验证的回退路径；
- 构建、发行资源和故障排查文档同步更新。

## 12. 小地图全局视觉定位实施状态（2026-08-24）

定位主链路已从“坐标 OCR 给出附近搜索种子”切换为“视觉词倒排粗检索、相似变换
RANSAC 几何验证、局部连续跟踪”。OCR 只把 160 地图像素内的同质量视觉候选提前，
无法升级拒绝结果，也无法独立发布。视觉索引缺失或损坏、候选歧义、小地图隐藏和窗口
失焦均保持可信位置至多 2 秒，随后隐藏位置标记。

- `Map_visual_index.imx` 使用 `IMAOIX01`、固定 4096 词、3640 个重叠分块以及完整负载、
  词表和源 IMF SHA-256；当前基础资源为 23,974,728 字节并覆盖 247,389 条基础特征；
  Dreamzhou 正式包和候选包分别生成 3,158,360 字节、382 分块与 2,117,248 字节、6 分块
  的 `visual-index.imx` 分片。分片引用相同词表，运行时只合并倒排表和只读特征行；
  生成器执行临时文件、完整回读、词表兼容和确定性校验；
- 强结果要求至少 12 内点、35% 内点率、3 px 中位误差、三个象限和无相近第二候选；
  中等结果要求两帧中心相距不超过 12 像素后才发布；
- 正常跟踪在上一中心 120 像素范围内复用同帧 SURF，以相似变换估计中心；连续三帧
  失败转全局恢复。历史 upright SURF 数据的旋转恢复只在常规检索拒绝后比较离散方向的
  粗分数，并只对前三个方向做精确验证；
