## 五阶段实测结论（后续补充，优先于初始静态推测）

本机 2026-10-20 12:03–12:11，用户只启用梦枢天罗，现有客户端未重启，每段约 31 秒、31 组样本；CPU 按 16 个逻辑处理器归一化。表中仅 CoreHost，内存来自进程完整 WorkingSet64 / PrivateMemorySize64，不等同于任务管理器进程页截图的内存列。

1. CPU 持续负载已复现，集中在 CoreHost，非只在启动时出现。静止大地图无 OCR / 无缓存重建仍有约 12.9% CPU；拖动时 74 次缓存构建，匹配中位耗时从约 42 ms 增至 274 ms。小地图阶段则持续出现 tracker-stalled / 恢复 / OCR 接管，应按两条路径分别分析。
2. 停止探索后 CPU 和新增识别日志均停止，工作集比第四阶段末尾低约 347.2 MiB、private 低约 442.9 MiB；线程 92 → 40、句柄 714 → 391。已排除“点击停止后仍持续满速识别”作为当前主要解释。
3. 停止后仍有约 458.7 MiB private，明显高于首次 start-accepted 的约 172 MiB。源码确认 Stop / App::StopTasks 取消任务并销毁会话截图与覆盖层，但未调用全局 OCR / 大地图 / 视觉定位器 / 特征仓库的 Shutdown；这些对象及其缓存继续有所有权，DLL_API.cpp::Shutdown 才统一释放。当前未做分配栈 / 堆对象计量，不能把余下增量精确归给某个缓存，也不能证明全部都是活跃对象而不是分配器保留。
4. 本轮没有观察到阶段内持续无界增长；高常驻、临时峰值和可复用对象保留均已存在证据，内存泄漏仍未证实。全地区 755 MiB 的静态核算不适用于这次单地区会话。

优先后续工作：大地图静止时分解预测 / 特征提取 / 周期匹配 / 捕获的 CPU；拖动时分解候选复制与 FLANN train 并做缓存命中对照；小地图核查视觉失配原因及恢复和 OCR 并行成本；分别测全局组件生命周期的内存。需要优化时，保持现有定位准确率、Direct OCR 显示和分层规则，不以直接关闭校验或降低频率替代对照。

## 1. 全地区启用时，资源自身就有较高常驻成本

### 后续现场信息与解释修正

用户随后提供任务管理器截图：CoreHost 在游戏运行前为 154.1 MB、CPU 0%；运行后为 736.6 MB、CPU 20.7%，内存增加 582.5 MB。WinUI 为 60.5 → 71.4 MB，Launcher 为 35.2 → 35.2 MB。截图是两个时刻的显示值，不构成泄漏或持续 CPU 负载的证明。

用户明确这次只启用梦枢天罗，其余地区关闭。main 对应资产为地图 41,424 点（描述子与关键点约 21.33 MiB），8 份楼层共 15,323 点（约 7.89 MiB），合计约 **29.22 MiB**，不含视觉索引与采样等附加数据。因此不能用下文的全地区 755.17 MiB 数据量解释本次增量；先前对话中称“新增内存与地图展开规模相符”的归因证据不足，撤回该归因。

加载时机已沿调用链确认：WinUI 首页 `StartPage.xaml.cs` 加载时调用 `EnsureStartedAsync`（试运行健康确认也有启动入口）→ CoreHost 入口调用 `Initi()` → `DLL_API.cpp` 调用 `BeginPreload` 并 `LayeredMap::Install`。地图后台展开、楼层读取不等待游戏或“开始探索”。App::Init 在开始探索后再次调用 BeginPreload，但 started_ 门控避免同一仓库重复加载，随后 AwaitReady 等待先前任务并初始化定位器、捕获；OCR 延迟到后续定位流程预热。

单地区配置是否确实进入当时宿主，仍须以该会话资源快照和 resource-load / layered-floor-index 日志核对；界面勾选本身不能证明已运行宿主加载的内容。若快照确认为单地区且预加载已完成，582.5 MB 的增量应优先分解捕获、模型、定位缓存和临时内存，不能继续归给全量地图特征。

对 main 跟踪的全部 112 个 IMF 文件读取头部；使用 `git hash-object --path=<相对路径> <本机已水合文件>` 与 `git rev-parse main:<相对路径>` 比对，每个文件一致。没有下载 LFS 内容，独立工作树中的 LFS 指针没有被当成资源读取。

## 2. 启动 / 资源切换存在可解释的临时峰值

`RuntimeFeatureRepository.cpp` 中 `kuroPacks`、`candidates` 保存各包数据，`AppendFeatureBatch` 再一次性分配合并矩阵并复制。这减少了反复 vconcat，却仍有原始包与合并结果共存的窗口；全部地图描述子会有约两份的瞬时存储，不能把峰值都称为泄漏。

尤其 `RecordMemory("resource-load-complete")` 位于这些局部容器销毁之前。该行读数是加载阶段读数，不能直接当“加载后稳定常驻”。需要补在局部容器销毁后的测量，才能算实际释放多少。

此外 `curatedCandidates` 仍被追加候选特征，但在 `src` 搜索只发现声明和写入，没有读取。对本次 14 个地图包的成本不应追加这个数字；若用户快照选了候选包，再核算该副本，优先级低于地图及楼层主成本。

## 3. 大地图：缓存预算没有覆盖真实内存，构建期间可叠加旧缓存

证据位置：`App/MapViewportLocalizer.cpp::GetLocalMatcher`、`App/MapViewportCandidates.h::SelectSceneCandidates`。

- 每次 miss 先复制候选描述子、按行 push_back，去重，再创建并 `train()` 一个 `FlannBasedMatcher`。
- 默认 48 MiB / 16 条的预算中，`cache.bytes` 仅含描述子逻辑大小及关键点 capacity；不含 FLANN 内部索引及其存储、描述子可能存在的额外 capacity、key / 容器和构建临时内存。**48 MiB 不是实际缓存内存上限。**
- 先 train 新条目，再驱逐旧条目，因此构建峰值包含旧缓存和完整新条目；预算无法约束这个阶段。
- 若单条超过预算，会驱逐所有旧条目后仍插入该条。检索宽档预算为 80 MiB，而缓存默认 48 MiB，因此代码允许超预算候选；是否在现场真的选满，需要看候选行数。
- 关闭地图的 `CancelPending()` 只清请求、结果并推进 epoch，不清 `localMatchers_`；缓存到 Shutdown 才清理。故关闭地图不保证立即回到打开前内存。

这些机制足以使匹配时 CPU 与内存一起上升，尤其冷启动、候选窗口改变、失败后扩大搜索时。具体占用和缓存抖动频率需要测量，不用源码注释里的旧毫秒数代替。

## 4. 大地图：取消不能打断最贵的内部步骤

worker / 请求有 epoch 和检查点，但 `SelectSceneCandidates()` 内部没有取消回调，`train()`、`knnMatch()`、SURF 特征提取内部也没有本项目的检查点。App 的请求看门狗为 20 秒；它不是 CPU 时间配额，也不能证明单个原生调用会在期限内停止。

因此用户拖动、关闭大地图或请求被替换后，旧的候选构建 / OpenCV 调用仍可能继续一段时间占 CPU。结果不再发布，与计算及时停止，是两件事。

建议先对同一固定帧记录候选提取、索引训练、匹配、几何验证分项耗时及进程 CPU 时间；对构建过程做“开始后关闭地图”的取消实验。基于测量再决定优化候选复制还是索引训练，不能只缩短看门狗。

## 5. 小地图定位：精确匹配与 OCR / 视觉恢复可并行叠加

`Coordinate/VisualLocalization/GlobalVisualLocalizer.cpp::MatchRows` 调用 `MatchDescriptorsExactly`。后者用 `batchDistance` 计算全部候选行与查询行的精确 L2 距离，并在 C++ 循环找双向近邻。工作量随两侧行数及描述子维度增长；2 MiB 距离块约束的是临时矩阵，不是总计算量。

全局恢复 worker 每次尝试有约 350 ms 的墙钟截止检查，App 的恢复提交间隔至少 150 ms。长期失配时可持续进行恢复计算；不能从这两个数直接推算 CPU 百分比，因为请求在途、取消、提交及线程并行都会影响实际占用。

`FeatureRowCache` 默认 64 MiB，超预算子集仍创建并使用，只是不缓存；活跃 shared_ptr 也可以让被淘汰数据继续存活。64 MiB 同样不是进程内存硬上限。正常跟踪与全局恢复要分别测量，不能把失配恢复负载当成所有正常定位的负载。

OCR 接管期间 `ReadoutWorkSchedule::SubmissionInterval()` 为 100 ms。当前 YOLO 每次 Recognize 对 raw / contrast 各执行一次 Detect；可持续处理约 10 次请求/秒、对应约 20 次模型推理/秒是调度允许的量级，实际还受推理耗时、在途请求及帧新鲜度限制。YOLO 的 intra-op 为 4、inter-op 为 1，intra-op spinning 已关闭；视觉恢复有独立 worker，可以与它同时工作。未发现 `src` 对 OpenCV 使用 `setNumThreads` 设置全局线程上限，实际 OpenCV 后端及线程并行度还需运行时确认。

应比较“视觉锁定”“持续失配”“OCR 接管”三个阶段的 CPU 时间、推理次数和帧延迟。不能在未验收准确率、接管延迟和显示连续性前直接降低识别频率或改匹配语义。

## 6. 截图和界面属于基线开销，也要纳入对照

`SimpleCapture::ApplyMinUpdateInterval` 已请求 33.333 ms，支持与失败均有日志；不支持该 API 的系统仍走原始到帧节奏。生产路径仍有整幅 GPU→CPU 回读及内存拷贝，`m_latestFrame` / `m_scratchFrame` 复用缓冲而非每次新分配。2560×1440 BGRA 每幅约 14.06 MiB，仅一次全幅拷贝在 30 Hz 时就涉及约 421.88 MiB/s 的像素量；这不是所有拷贝的总量，也不是内存常驻量或 CPU 占比。

App 消费侧 80 ms 的 idle 节奏不会自动把 WGC 回调限到同样节奏。ROI 路径属于可隔离验证的实验，不能当成所有用户已启用。

CoreHost 状态报告为 200 ms，WinUI 手柄定时器为 16 ms 且有 enabled 门控。这些路径需要在“未开始探索”的基线中测量，目前没有证据把它们列为主要 CPU 来源。

## 8. 下一轮实机对照与优先级

### 新反馈：大地图标记出现后鼠标指针轻微卡顿

后续已收到该玩家的 `Logs (4).zip` 并完成现场分析：见 [`PlayerCursorStutter_20261020.md`](PlayerCursorStutter_20261020.md)。玩家实际记录的构建与输入服务间隔比下面本机旁证严重，优先参考该报告；以下保留收到日志前的假设与验证思路。

用户转述玩家观察：标记未加载时鼠标顺滑，标记加载后出现卡顿。尚无该玩家的鼠标事件延迟、游戏 FPS 或对应日志；以下是 main 调用链及本机既有采样的旁证，不能认定为玩家现场已证实根因。

第一嫌疑是**鼠标低级钩子与渲染 / 跟踪共用线程**。`ImGuiOverWindows.cpp` 在覆盖层线程调用 `DrawMarkerInteraction::Initialize` / `BeginFrame`；`DrawMarkerInteraction.cpp::SyncMouseHook` 依据 mapInteractive / regionsAt / 拖动状态安装 `WH_MOUSE_LL`。`DrawMap` 发布交互状态和命中区域，因此进入有可交互地图覆盖的状态会新增鼠标钩子路径；钩子不一定严格以标记数量非零为条件，不能仅凭玩家描述推导精确开关时刻。

该线程同时执行 `mapMotion.Update`、路线与标记绘制、布局、draw-data 哈希和 DX11 提交。在相邻 `pump()` 之间进行这些工作，鼠标钩子的服务机会可能被延后。`FramePacer` 已在帧等待期间通过消息感知等待处理消息，故不能简单归因为 Sleep(33 ms)，也不能宣称鼠标被硬性锁成 30 Hz。普通 WM_MOUSEMOVE 分支没有无条件遍历所有标记命中区域，并且最终放行移动；“故意吞掉鼠标移动”也没有代码证据。绘制与输入共线程的非等待工作段仍是问题候选。

复核本机第二阶段的 15 个 overlay-motion 日志窗口：mouse hook 全部 on；各窗口 `inputGapMs`（该窗口最长主动工作段消息处理间隔）为 **11–19 ms**，`motionMs` 最大 **18 ms**、`presentMs` 最大 **2 ms**、segBuildMs 窗口均值的平均约 **6.45 ms**。第三阶段 16 个窗口 inputGapMs **13–23 ms**、motionMs 最大 **23 ms**、presentMs 最大 **1 ms**。这些数值是线程分段观测，并非逐鼠标事件的实测延迟或 P95；但显示现有覆盖线程确有约十几毫秒的服务间隔。本机这两段 Present 时间较小，优先测画面跟踪与绘制段的输入耦合。

第二嫌疑是覆盖绘制 / 合成影响游戏帧率；若游戏使用软件光标，帧时间变差也可表现为指针不顺。需要玩家区分“指针本身停顿”与“指针仍动但地图拖动跳跃”，并同步游戏帧时间。已有本机 CPU 12–16% 是进程总量，不能据此直接解释输入延迟；局部线程阻塞比总 CPU 更有辨别力。

建议因果对照：先记录标记显示前后 hooks / inputGapMs / motionMs / segBuildMs / segPresentMs 与游戏帧时间；再在开发诊断中做 A/B/A **保持相同画面跟踪、标记绘制、窗口和 Present，仅临时关闭鼠标钩子**。若指针恢复顺滑，优先将钩子迁到专用消息线程，通过不可变命中快照处理输入，避免读文件、重计算或等待渲染锁。若不改善，再单独隔离绘制 / 窗口呈现。简单“关闭标记”会同时改变绘制、钩子、可见窗口等，无法区分原因。本轮未实现诊断开关或改动玩家安装。

## 第二轮：保留原编码与全局搜索协作预算

### 已实现的边界

- v2 IMF 原来已经存储 128 列 byte 编码。生产共享地图和完整楼层特征保留这些原始字节及各包解码参数，只在需要的候选行或一个楼层投票期间展开为 float；计算公式与旧加载器逐位相同，没有再次量化或删特征点。旧 v1 继续保持 float；混合包合并只展开，不重新量化。
- 候选构造先确定去重后的行号、释放持有描述子的去重表，再创建精确大小的 float 矩阵；恢复缓存和 OCR 场景窗口使用同一路径。128 列 float 的去重身份按实际 512 字节内联保存，仍然拥有其字节。
- 楼层完整证据、ownArt、采样 stride、场景歧义和几何接受阈值不变；不改变开放层规则或 `ArtIsSurfaceCopy`。
- 全局搜索在一次请求内复用同一个 region/factor 的截图特征。约 2 秒软预算只在完整场景组之间检查，当前组的所有候选场景必须检查完才接受；下次请求从后续组开始，但对新截图重新取证，仅保存遍历下标。local512 不受这个全局预算影响。OpenCV 调用和完整场景组可能超过预算，不能把它称作硬 2 秒上限。
- 取消检查覆盖候选构造、train、knnMatch、几何验证边界；异常与取消都有显式诊断。增加 `budgetExhausted/groupsTried/nextGroup` 字段，增加释放临时包之后的 `resource-load-retained` 读数，避免把加载峰值称为稳定常驻。
