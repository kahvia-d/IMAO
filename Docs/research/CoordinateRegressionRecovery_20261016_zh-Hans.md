# 飞行补训后的退步恢复与单张推理核验

日期：2026-10-16。用户授权继续解决上轮退步。本轮不再训练、不改标签或原模型权重，验证字符冲突处理与自有旧权重后备。**实际 CPU 单张回放中，之前会话由 1016 正确提升到 1044，新飞行素材由 353 提升到 362，已知 XY 零错误。上一轮严格保护基线的正确帧全部保留；代价是后备路径增加平均处理时间，没有默认接入客户端。**

## 根因与改动边界

上轮之前会话新增 20 张正确、丢失 26 张正确，净少 6。26 张损失中：

- 20 张原图路其实正确，增强路同时返回一个很强的正确字符和较弱的另一类别，例如 `4=0.98、3=0.27`；旧保护把任意另一类别视为冲突，直接拒识。
- 3 张原图路本身存在类似的重叠字符候选，冻结解码器因此拒识。
- 另外 3 张缺少必需的逗号，无法形成完整 XY。

本轮只做离线研究探针。检测 conf=0.25、IoU=0.45、max_det=256、原有预处理、解码器、布局和补负号逻辑保持原样；没有修改旧报告、评分、标签、权重或旧失败断言。新保护的证据框对应 IoU≥0.50、候选下限 0.25 沿用前轮；**分数优势至少 2 倍**作为新试验规则在全量回放前固定，没有扫参数或逐帧例外。

新增规则要求增强路最强字符与原图路一致，存在其它类别时还须达到至少 2 倍分数。只对同位置的数字候选做处理，不插入缺失数字、负号或逗号。原图路若也有重叠数字，只有原图最强数字同样占至少 2 倍优势，且获得增强路相同优势确认，才去掉较弱数字；范围限于已观察到的两个逗号之前，Z、日期和时钟不参与该消歧。符号冲突仍交给原有解码器。

先写了 10 个行为测试：较弱替代、接近竞争、缺少第二路、两路不一致、原图消歧、符号保护、可选 Z 等。以旧行为运行有 2 个预期失败，加入新探针后 10/10 通过；另以禁用探针的回退对照再次得到同样 2 个失败。测试还明确展示两路一起认错时仍可能放行，不把相关证据称作独立互证。

## 消融回放与后备路径

复用上轮实际 CPU 检测框，分别检验新规则的两个组成部分。表内为正确／错误／拒识；全部是已观察数据的开发回放。

| 处理方式 | 之前会话 1063 张 | 新飞行素材 386 张 |
|---|---:|---:|
| 上轮冻结保护 | 1016／0／47 | 353／0／33 |
| 只调整增强路冲突判断 | 1037／0／26 | 358／0／28 |
| 只处理原图数字重叠 | 1017／0／46 | 354／0／32 |
| 两项合用、仍为单模型 | **1039／0／24** | **361／0／25** |

单模型组合将原先 26 张损失中的 21 张恢复，但仍有 5 张退步：之前会话 24、538、604、654、677。没有为了消除剩余拒识而补逗号或跳过确认。

进一步验证了**自有旧权重后备**：先运行本项目 flight 权重和新保护；只有它拒识时，才运行本项目旧 expanded 权重，并完整使用旧的冻结解码、补号与严格数字保护。后备返回的是整组坐标，不拼接模型的数字；主模型已有返回时不会调用旧模型，也不会被旧模型覆盖。两个权重都来自官方通用 YOLO11n 谱系和本项目自有标注，不使用网友的游戏专用权重。

## 实际单张推理结果

重新运行了 GPU PyTorch **单张**和 CPU ONNX **单张**，各 2012 个有效输入；旧 835 排除规则不变。每个输入先跑新模型的 raw／contrast 两路，必要时再跑旧模型两路。

| 当前 CPU 路径 | 旧开发 170 张 | 之前会话 1063 张 | 新飞行素材 386 张 | 历史留出 72 张 |
|---|---:|---:|---:|---:|
| 单模型新保护 | 166／0／4 | 1039／0／24 | 361／0／25 | 71／0／1 |
| 新保护＋旧权重后备 | **167／0／3** | **1044／0／19** | **362／0／24** | 71／0／1 |

对照补训前 expanded 的**严格保护**输出，1607/1607 张已知正确帧均保留；对照上轮 flight 的实际 CPU 严格保护输出，1630/1630 均保留。因此上轮报告中的严格保护退步已补回。这个结论不包含所有历史无保护返回：旧 expanded 的原管线有 1622 张已知正确，当前组合保留 1619，之前会话 506、593、596 仍拒识，不能概括成所有历史返回都恢复。

本轮后备调用 345/2012 次，返回 8 次，其中 7 次已知正确，1 次待定；后者不计正确。新素材 46 张、旧开发 141 张、之前会话 87 张无坐标均零误报。旧开发 8 张待定中返回 3 张，之前会话 11 张待定中返回 3 张，新素材 3 张待定中返回 1 张；仍没有把未知返回默认判为正确。

旧 415 耀光帧继续正确返回 `(-17,-7786)`；新 21 帧的原图 `8159→8150` 错误仍被保护挡住。上述改善不依赖把这些返回改成标签。

## 批量边界问题与严格核验

上轮 GPU batch=32 与 CPU 单张仍是 **2011/2012** 一致，原失败结果和原全一致断言完整保留。88 帧逗号分数在该门槛附近：批量 GPU 0.2501344，而 GPU 单张 0.2493666、CPU 单张 0.2499107。没有降低 0.25 去追求表面一致。

本轮将实际核验入口与部署输入方式对齐，采用 batch=1，运行新的完整回放；主模型和带后备路径的 XY、可选 Z 四项都达到 **2012/2012 一致**，仍使用“所有 2012 项必须相等”的严格判据。88 帧在主模型两端都拒识，后备旧模型两端都可读对。因此这是统一单张入口后的新证据，不能把上轮批量结果改写成通过，也没有证明任意批量大小都一致。

外部核验重放了 4024 条实际输出及后备分支，核对两个锁中的文件、先前已入库脚本和标签摘要、1577 组旧原生图像摘要、435 组新原生输入与两路像素摘要、全部计分和逐帧保留情况。独立审阅也重新计算了 CPU/GPU 一致性、计数与保留情况。

仍有可复现性限制：临时 runtime runner 本身只在运行前后检查了部分直接依赖，没有在入口直接核验所有传递依赖；上面对所列源码、标签与输入证据的核验属于**运行后的外部审计**，没有发现漂移，但不代表所有运行库均已固定，也不冒充 runner 已自带完整门禁。正式实现前应将这项检查纳入入口。

## 耗时与采用边界

CPU 在同次预热后回放中测得：

| CPU 处理时间 | 单模型 | 带后备 |
|---|---:|---:|
| 平均 | 44.43 ms | 63.09 ms |
| 中位数 | 29.43 ms | 29.82 ms |
| P95 | 154.38 ms | 261.64 ms |

后备触发约 17.1%，平均多 18.66 ms，约增加 42%；整次回放累计增加约 37.55 秒。统计排除模型初始化、读取图像文件，包含两路检测与后处理；不是隔离性能基准，也不是游戏实机帧率测量。不能只看中位数接近而忽略平均和尾部开销。

因此目前保留两个候选：单模型新保护降低过度拒识、开销较少；双权重后备恢复此次严格保护基线的全部已知正确帧，但需额外耗时。没有默认将双模型接入客户端。

所有会话都已用于分析。原 72 帧留出如今也只能称为历史观察回放，不再承担新保护的独立验收作用。已知零错误不代表未来零错误；两路相关输出或旧模型都可能产生共同错误。后续应先把选定方案做成正式离线入口、补齐依赖门禁与性能核验，再用新会话验收。玩家目录、开发客户端、托管代码、XAML 和交付树均未改动，本轮无下载。
