# 换检测器（SURF → SIFT）：决策实验与结论（2026-10-08）

> 起因：群友建议换 SIFT，理由是"特征点少几个数量级、所有地图加起来才 20 多 mb、imao 原项目的
> 特征点筛选很烂"。本文是围绕这句话做的测量、被推翻的数字，以及结论。
>
> **一句话结论：他的方向对，但 20 MB 那个数字不成立——我们的实际收益是 2.4 倍，不是 8 倍；
> 而其中一半的收益根本不需要换检测器。**

## 一、结论摘要

| 问题 | 测量结果 |
|---|---|
| 换 SIFT 能省多少？ | 192.75 MB → **81.84 MB（2.4x）**；若同时把重复词汇表只发一份 → **55.84 MB（3.5x）** |
| 有没有更便宜的大头？ | **有。索引里 28.00 MB 是同一份 2 MB 词汇表被复制了 14 份**，去掉它省 26 MB，且**零算法风险** |
| 群友说的"筛选"起作用了吗？ | **没有。** 在他给的 `g150_mpc200` 参数下网格配额从不触发；10x 全部来自检测器本身 |
| 质量够吗？ | 合成裁剪 139/168（82.7%）通过，但 **fabricatorium 只有 4/12**，未解释 → ⚠️ **2026-10-10 已解释，见文首** |
| 现在该换吗？ | **不该。** 见第七节 |

## 二、方法：先修三个会让结论跑偏的缺陷

任何一条不修，下面的数字都是错的。

### 1. 参照特征必须在**逐张 1024 瓦片**上抽取

生产的 [`tools/KuroMapFeatureBuilder/main.cpp:230-242`](../tools/KuroMapFeatureBuilder/main.cpp#L230-L242)
是一张一张瓦片跑 `detectAndCompute` 的。而旧的对照脚本在**整张拼接大图**上跑一次。
SIFT/SURF 的八度都是相对"喂进去的那张图"建的，9216px 画布和组成它的 196 张瓦片**不是同一个实验**。

实测差距：整图协议 8 包 64,898 点；逐瓦片协议 14 包 216,502 点。
**旧协议把关键点数低估了约 3.3 倍**——这正是它算出"7.3 MB"的原因。

对照脚本新增 `--reference-mode`，默认 `per-tile`。

### 2. 对照脚本读不了 v2 特征二进制

`load_imao_features` 硬编码 `descriptor_type == 1`（v1 float32）。10-08 的量化迁移之后，
所有包的 `.imf` 都是 v2（uint8 + deflate），脚本直接抛错。已按 `FeatureBinaryCodec::Load`
的真实布局补齐 v2 读取（`(code + descriptorOffset) * descriptorScale`）。

### 3. 两个会静默给出错误数字的脚本缺陷

- **`grid_sample` 用栅格矩形去网格化"应用地图坐标"下的已发布关键点** → 恒定保留 0 个，
  却报告成"配额只保留了 0%"。已加 `bounds` 参数。
- **`evaluate()` 覆盖同名的 config 条目**，把 `log_size()` 刚算好的体积数据整个丢掉。
  这就是磁盘上那些旧 JSON 只有精度、没有字节数的原因。已改为合并。

## 三、否证：三个流传中的数字都不对

### ① `imao-surf-13329: verified=0` —— 脚本残骸，不是 SURF 的表现

```
SURF_create FAILED: OpenCV(5.0.0) ... This algorithm is patented and is excluded
in this configuration; Set OPENCV_ENABLE_NONFREE CMake option and rebuild
```

Python 的 OpenCV wheels **根本创建不了 SURF**。旧版脚本把这个异常记成了一列零。
当前脚本已经删掉那一列并写明原因，但**磁盘上的旧 JSON 还留着它**——见
[`measurements/SUPERSEDED.md`](../measurements/SUPERSEDED.md)。

推论：**我们至今没有 SURF 与 SIFT 的公平对照**。SURF 侧只能用生产实机表现当基线，
而这恰恰是"换检测器"最该问的问题。

### ② "所有地图加起来 20 多 mb" —— 口径是"只有特征"，而且低估

逐瓦片实测：14 包 SIFT 特征 **23.44 MB**（v2 编码后）。这个数字**和群友的说法量级吻合**，
但注意两件事：

1. 它**只是特征**。我们的视觉索引是另一块，而且是更大的一块（当前 112.20 MB）。
2. 群友的 wuwa-map 用不用我们这种词汇表索引、索引多大，我们**没有测量过**，不能假设为 0。

### ③ "特征点筛选很烂" —— 方向对，但他的筛选参数不起作用

生产是 `SURF::create(60, 8, 4, true, true)`（[`main.cpp:227`](../tools/KuroMapFeatureBuilder/main.cpp#L227)）
——hessian=60、**没有任何质量筛选或密度配额**，117 万点摊到约 600 张瓦片 ≈ 每张 2000 个点。
"大部分特征点质量低"这个判断**是对的**。

但群友方案里的 `g150_mpc200` 网格配额**从未触发**：150×150 格 × 每格 200 = 450 万预算，
而最密的包也只检出 5.3 万点——**算术上就不可能触发**。tethys 上的实测也一致：
带配额与不带配额的关键点数（3097）与逐条内点**逐项相同**
（[`accuracy-check/tethys-grid-check.json`](../measurements/accuracy-check/tethys-grid-check.json)）。
**所以那 10x（实际是 5.4x）全部来自检测器更换，不是筛选。**

反向证据——如果把"按 response 排序"的配额套在**现有** SURF 点上（50×50 格、每格 20）：

| 包 | 配额保留率 |
|---|---|
| jinzhou | **3.6%** |
| lahai | 5.7% |
| qiqiu | 12.2% |
| … | … |
| tethys | 68.8% |
| timeriftruins | 99.9% |

**它对最密的包砍掉 96%，对稀疏的包几乎不动。** 这与生产代码里遗留的那条理由一致
（"按 response 给单元格排序会丢掉安静地形，只留下密集的城市/等高线"）——
那条注释随初始导入提交 `0a05704` 进来，很可能是 imao 原作者的决定，而群友批评的正是它。
**结论：按 response 的全局配额是错的工具**，要用也得先想清楚按什么度量、留多少。

## 四、体积：实测与逐 section 投影

### 现状（14 包，实测）

```
特征            80.55 MB
索引           112.20 MB
  vocabulary    28.00 MB   ← 14 份完全相同的 2.00 MB 拷贝（1 个不同哈希）
  tile 表        0.31 MB
  histogram     17.56 MB   ← 6730 个索引瓦片的稀疏 TF-IDF
  featureRow    39.98 MB
  posting       26.35 MB
合计           192.75 MB
```

### 投影：只有两个 section 随关键点数变化

关键点 1,176,080 → 216,502（**18.4%**）：

```
特征            80.55 MB → 23.44 MB   (3.4x)
索引           112.20 MB → 58.40 MB   (1.9x)   ← 只有 1.9 倍
  固定部分      45.87 MB  （vocabulary + tile + histogram，完全不随点数变）
  缩放部分      66.32 MB → 12.21 MB  （featureRow + posting）
合计           192.75 MB → 81.84 MB   (2.4x)
```

**这就是"20 MB"不成立的机制**：索引里 41% 的内容与关键点数量无关，
而索引本来就比特征大。

### 独立于检测器的一笔：词汇表去重

14 个分片各自内嵌**同一份**词汇表（4096 词 × 128 列 × float32 = 2.00 MB），
哈希只有一个值。只发一份：

```
索引            58.40 MB → 32.40 MB
合计           192.75 MB → 55.84 MB   (3.5x，且不需要换任何算法)
```

这比换检测器**更便宜、风险更低**，收益却接近它的两倍。

## 六、质量判据：现状

运行时的判据是**绝对内点数**，不是密度相对值（[`GlobalVisualLocalizer.cpp:897-904`](../IMao-Core/src/Coordinate/VisualLocalization/GlobalVisualLocalizer.cpp#L897-L904)、
[`RecoveryPolicy.h:9`](../IMao-Core/src/Coordinate/VisualLocalization/RecoveryPolicy.h#L9)）：

| 等级 | 条件 |
|---|---|
| Strong | 内点 ≥ 12 且 内点率 ≥ 0.35 且 重投影中位误差 ≤ 3.0px 且 覆盖 ≥ 3 象限 |
| Marginal | 内点 ≥ 8 且 内点率 ≥ 0.25 且 中位误差 ≤ 4.5px 且 覆盖 ≥ 2 象限 |
| 重捕获 | 内点 ≥ 6 且 比率 ≥ 0.20 且 象限 ≥ 2 |

**修正我先前的一个说法**：这些阈值不是"围绕旧密度定的"，它们是绝对计数，
所以点少 5 倍**不会自动**让它们失效。真正的风险在分布的**下尾**：
原来能出 20 个内点的查询掉到 8–10 个，质量就从 Strong 掉到 Marginal。

但——**合成裁剪协议无法用来标定这件事**：合成查询是在**原始分辨率**上取的 184px 裁剪，
而真实小地图是另一个尺度（拉海洛记录的 `minimapScale` 是 2.15）。
内点数是绝对量，跨尺度不可直接换算。
**所以判据重标定必须用真实尺度的证据，这次的数据不够。**

## 七、结论与建议

### 不建议现在整体换 SIFT

三条理由：

1. **收益是 2.4x，不是 8x**，而其中最大的一块（词汇表 26 MB）**不需要换检测器**。
2. **fabricatorium 的 4/12 没有解释**。换检测器会动到全部 14 个包、参考图验证、
   四点校准之后的全部验证链；带着一个未解释的质量异常进去是不负责任的。
   > ⚠️ **2026-10-10：已解释，本条不成立**——那 12 道题里有 7 道任何检测器都答不出，
   > 换成纹理门禁后同一个包是 11/12。见 [`OpenWork.md`](OpenWork.md) 第 7 节。
3. **我们还没有一次公平的 SURF↔SIFT 质量对照**（第三节①）。目前只有"SIFT 在合成裁剪上
   82.7%"，没有"SURF 在同一个测试上多少"。拿这个去替换一个正在线上正常工作的东西，证据不足。

### 建议的次序（互相独立，各自可验收）

| 优先级 | 事项 | 预估收益 | 风险 |
|---|---|---|---|
| **1** | **词汇表去重**：分片不再各自内嵌词汇表，改为共享一份（按 `vocabularySha256` 引用） | **26 MB** | 低——编码层改动，有 `IMaoVisualIndexProbe` 与词汇表一致性断言兜底 |
| **2** | **查清 fabricatorium**：为什么一半查询零匹配 | 解开迁移的拦路石 | 无（只读排查） |
| 3 | **histogram 压缩**：6730 个索引瓦片共 17.56 MB（约 2.7 KB/瓦片）的稀疏 TF-IDF，权重换窄类型 | 5–9 MB | 中——要重新验证检索排序不变 |
| 4 | **公平的 SURF↔SIFT 对照**：用真实尺度的裁剪，两边同协议 | 决定要不要迁移 | 需要 C++ 侧探针（Python wheels 没有 SURF） |
| 5 | 换检测器 | 58 MB（若 1 已做，则约 32 MB） | 高——全量重抽 + 全链验证 |

**1 和 2 可以立刻做，且都不需要新分支。**

### 关于"新开分支"

你原来的直觉——"在旧数据上改出新的东西，越改越乱"——**在数据层是完全正确的**：
词汇表全 15 个索引共用且对输入敏感，所以任何换检测器的动作**必须**全量重抽 + 全量重建，
没有第二种做法。但：

- **现在还不该开那条分支**，因为换不换还没定（第二节③、第七节）。
- 真要开的时候，正确做法是**先把"词汇表去重 + 防护网"这类正交成果并入 main**，
  再从那条干净的 main 上开新分支做"新检测器 + 全量重抽 + 全量重建"。
  这样新分支站在只含正交基础设施的基线上，而不是在旧数据上改。
- 好消息：新分支反而**更简单**——"必须复用旧词表"这条枷锁在全新重建里不存在
  （15 个索引自然共享新词表），四点校准与坐标变换**一个字节都不用动**。
