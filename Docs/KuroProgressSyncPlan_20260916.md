# 库街区浏览器扩展与点位进度同步计划

状态：阶段 1-4 与阶段 6 的自动同步已实现并通过仓库回归；阶段 5 的失败/并发恢复只覆盖已实测的部分。
仍未验证的边界：真实浏览器内的完整交互、多标签页、以及除单点往返以外的批量写入。

## 目标与范围

首版支持 Windows 上的 Chrome/Edge，将当前用户库街区账号的点位完成状态与 IMao 双向同步，包括取消完成。首次连接先预览差异，再选择同步策略。默认手动同步，设置页可单独开启自动同步（见下文）。路线、筛选、攻略、游戏存档及自定义标记不在首版同步范围。

网页地址中的 state、country 是地图视图参数，不能用作账号身份，也不能把当前视野当成远端完整进度。

## 已核实的项目基础

- `IMao-Core/src/Runtime/MarkerCompletionStore.h`：已有 local/账号档案、原子写入、revision、remoteCompleted、pending、分页快照/outbox，以及初始化、远端应用、确认和冲突命令。
- `IMao-WinUI/Services/LocalMarkerProfileSelection.cs`：保留旧档案选择读取；不是登录服务。
- `IMao-WinUI/Helpers/UserDataPaths.cs`：用户进度在本机 SavedPoints 下。
- `BrowserExtensions` 当前无扩展实现；公开地图资源同步脚本不包含已确认的用户进度同步协议。
- 现有 markerResolveConflict 会更新远端基线并清 pending，不能未经远端确认直接用来表示“选择本地并准备上传”。实施时必须拆分冲突决策和远端成功确认。

## 架构与凭据

推荐：库街区页面 → 扩展会话适配器 → 扩展 service worker → Native Messaging Host → WinUI 同步协调器 → CoreHost 点位存储。

扩展仅在用户点击连接后读取库街区当前登录会话所需的 token，并通过经验证的身份接口确认其所属账号。token 默认保留在扩展内存/会话级存储，扩展负责访问固定的库街区进度接口；桌面程序接收账号身份和结构化同步结果。浏览器关闭、扩展重启或登录失效后重新获取会话，离线修改继续留在本地队列。

备选是将 token 经 Native Messaging 交给桌面端并使用 Windows DPAPI 保存，支持浏览器关闭后的同步，但需验证 token 是否能脱离浏览器独立使用，并增加凭据生命周期管理。另一备选是 localhost HTTP 桥接，安装简单但增加端口与网页访问控制，不作为首选。

第一阶段确认 token 实际在 Cookie、页面存储还是请求头中；仅选择必要的读取机制。不猜测字段名，不读取其他站点凭据，不把 token 写入日志、诊断截图、剪贴板、配置或导出文件。若会话依赖 HttpOnly Cookie，优先让浏览器携带会话执行固定请求，按实际机制申请最小权限。

Native Host 只允许明确扩展 ID；按当前 Windows 用户注册。首次由桌面端确认配对，绑定浏览器实例、安装实例和账号。消息携带 protocolVersion、requestId、accountId、sessionGeneration；切换账号或断开连接使旧世代失效。限制消息长度、请求种类、数据条数，分块传输快照，拒绝任意 URL、任意命令和任意文件路径。页面只能提交有限会话信息，不能决定云端写入计划；后台验证标签页来源、框架、URL 和账号。页面桥接本身不视为可信身份凭据。

Native Host 为薄桥接层，不写进度文件、不启动第二个 CoreHost。通过受当前用户访问控制的本地管道连接已运行的桌面同步协调器。考虑程序自更新目录变化，使用稳定注册入口；卸载时移除注册。多桌面实例或多标签页对同一账号只允许一个写入协调者。

## 点位与账号身份

云端身份必须来自认证结果，库街区账号与游戏 UID 不预设等价。先确认进度是否额外按游戏角色/服务器隔离；若存在，纳入档案绑定和每次请求校验。

点位至少用账号档案 + stateId + 上游 pointId 标识，验证上游 ID 唯一性；若需 country/floor 等命名空间，增加字段并做版本化迁移。不得用坐标、显示名称或分类替代稳定 ID。当前存储键是 stateId:pointId，需通过数据检查证明足够。

未知云端点位原样保留，不生成删除请求；本地未收录或未开放的场景不因此开放定位。资源删除/重编号先标记为待映射；不靠坐标自动合并。任何取消完成写入都必须针对明确点位。

## 首次同步

1. 验证账号、配对和同步范围；备份当前本地档案与完整远端快照。
2. 完整读取范围内所有分页，确认无分页缺失、无认证错误、无中途账号变化。失败/部分结果不能解释成空进度。
3. 展示本地独有完成、云端独有完成、共同完成、未知点位，以及将新增/取消的数量。
4. 用户选择：合并已完成（默认建议，仅首次取并集）；以云端为准（本地对齐）；以本地为准（仅覆盖已确认映射范围，列出云端取消项）。取消项需明确确认，未知项不清除。
5. 将选择生成带快照摘要和本地 revision 的计划；执行前重新读取，若发生变化则重新预览。
6. 已确认完成的部分建立基线；未确认部分保留计划与队列。全部范围核对后才显示本次同步完成。

现有 upload 模式只覆盖 localTouched 点，不等于完整“本地为准”。实现需显式定义未触碰本地点的语义并修正命令，不能只改界面名称。

## 后续合并规则

B 为上次双方确认一致的基线，L 为当前本地，R 为本次完整远端状态。

| 条件 | 处理 |
| --- | --- |
| L = R | 双方已一致，按对应 revision 确认，更新基线 |
| L != B 且 R = B | 本地修改，上传明确目标状态 |
| L = B 且 R != B | 云端修改，原子应用到本地 |
| 无可信 B 且 L != R | 进入首次合并/人工选择，不猜测新旧 |
| revision、账号、资源映射、快照完整性不满足 | 暂停相关操作，重新读取或要求处理 |

纯布尔完成状态在可信共同基线下，两边都变化会得到同一值，不需要虚构必然存在的“双方相反修改”冲突。缺失历史、修改后又撤销、并发读写期间的变化仍可能无法从最终值判断意图；有事件日志/服务器版本就使用，没有则明确只做状态同步。不使用本机时间戳推断哪端更新。

取消完成保存为显式 false 待同步状态，不通过删除本地记录表达。同步导入标记来源，避免再次进入上传队列。用户本地新修改不能被旧请求回执清除。

## 事务、并发与失败恢复

按账号/状态串行：拉取完整远端 → 获取稳定本地 revision → 生成差异 → 重新验证写入前提 → 持久化意图 → 分批写入 → 远端回读 → 按原操作 revision 确认。

优先使用“设置 completed=true/false”接口，不使用盲目 toggle。若只有 toggle，超时后必须先查状态再决定是否再次调用。若只有全量覆盖且没有条件写/版本号，首版关闭自动上传并重新设计写入范围；不能假装客户端能提供服务器 CAS。

如果远端支持 ETag/版本条件，写入携带它并处理冲突；若不支持，写前/写后读取只能缩小竞争窗口，不能保证与其他设备编辑的严格一致性。检测到变化则暂停该批并重新规划。

持久化 journal 包含操作 ID、账号、state、point、目标状态、本地 revision、基线和阶段。崩溃、断线或超时后先回读核对，再重试未知结果。部分成功逐项记录，失败项保留；不提前清空整批队列。备份主要用于本地恢复，云端恢复须重新比较并生成新操作，不能直接回滚整份旧快照覆盖其他设备修改。

401/会话失效暂停并提示网页重新登录；403 区分权限/接口变化；429 遵循 Retry-After；网络/5xx 有上限的指数退避加抖动；未知响应结构停止写入。自动同步开启后使用去抖和限流，具体频率按接口观察结果确定。

## 自动同步（已实现）

自动同步复用与手动按钮完全相同的并集流程（先推送本地点位独有的完成状态，再把库街区独有的完成点拉进本地），因此不会出现两套写入语义。

- 开关：设置页“库街区点位进度同步”中的“自动同步”，默认关闭；打开后写入本机设置 `kuroSyncAutoSync`，下次启动自动恢复。
- 时机：启动后 30 秒跑第一次，之后每 10 分钟一次；手动预览/应用会重置计时。
- 失败退避：连续失败按 1/2/4/8/16 分钟递增，上限 30 分钟；任一次成功恢复为正常间隔。
- 暂停而非重试：没有同步档案 ID、或该档案在本机没有库街区凭据时，不发起请求，状态栏说明原因。
- 结果可见：设置页显示最近一次结果（已是最新 / 推送 N 个、拉取 M 个），并按时间戳失效已缓存的预览，避免用过期差异写库。
- 互斥：手动与自动共用同一把锁，定时任务不会在用户应用预览的同时写入。

## 待第一阶段确定的外部条件

已从库街区地图前端静态资源确认：登录 token 使用 `AKI_MAP_USER_TOKEN`，账号来自 `AKI_MAP_USER_INFO.userId`；已完成点读取为 `POST https://api.kurobbs.com/map/core/position/getHaveDonePositionIds`，请求头包含 `token`、`source=h5`、`wiki_type=120`、`devcode` 和 `state_id`。

以下读写契约已于 2026-09-17 用真实账号实测（读接口多次、写接口含往返与重复调用）：

- **读取粒度是账号级**：`state_id` 只被要求携带，不参与过滤——同一个账号对 8 个不同 `state_id`（以及不带该头）返回**完全相同**的完成点集合。点位归属只能由本地点位目录推断，因此一次请求即可取全，再按目录分区。
- **写入完成**：`POST https://api.kurobbs.com/map/core/position/changeStatus`，请求头同上（`state_id` 为该点位所属区域），`Content-Type: application/json`，请求体 `{"id":"<点位id>","positionType":"<类型id>","status":1}`；返回 `{"code":200,"msg":"操作成功","data":true}`。
- **取消完成**：同一接口 `"status":0`（实测 43→42→43 往返可逆）。
- **幂等**：同一请求连续重复调用均返回 200，集合不重复、不增加；因此写入结果未知时可以安全重试。
- **字段来源**：`positionType` 等于点位目录里该点的 `typeId`；已全量校验本地 23,803 个点位，`typeId` 与目录分类 id 完全一致（0 处不一致），所以本地档案记录里的 `nameId` 可直接作为 `positionType` 使用。
- **限流与条件写**：服务端未提供 ETag/版本条件写（未观察到相关头）；限流数值尚未测定，实现按串行写入 + 429 退避处理。
- 服务端对请求形状敏感：缺少 `id` 或 `positionType` 会返回 `code=102` 及字段级提示（如“positionType 标点类型不能为空”），字段类型不符（如 `status` 传布尔）会返回 `code=102 服务器外部错误`。
