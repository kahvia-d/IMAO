## 结论及其边界

视频确实显示工具标记成批出现、消失，而地图底图基本不动。这次日志存在一个与反馈吻合的
场景差异：大世界的标记源帧明显更旧、生产更慢，附着绘制也更少；切到下层金库后恢复。
在一段持续 BigMap、持续前台、标记可见性不翻转的干净窗口中，日志还直接记录了
一分钟 190 次渲染不可用及 191 次恢复，证实渲染侧在反复通断。
因此，此前探针漏判或焦点丢失的解释**不足以解释这段窗口**。

目前最有证据支持的因果链是：场景相关的处理成本或锁竞争使标记源帧变旧，源帧或 UI
可见性证据随后在绘制门禁处过期，导致间歇撤绘。**尚未定案到某一个耗时函数**：
旧日志没有逐段耗时、实际 `maximumAge`、每道门的拒绝计数，不能把采样年龄超过
默认 500 ms 直接等同于已记录了一次源帧撤绘，也不能把“没有配准失败”当作没有撤绘。

本分支补充诊断，不改变位置可信度、显示时效、配准门槛或资源规则。
没有声称已修复 even 的问题，也没有改既有测试断言。

## 关键对照

统计只选择 `overlayMode=full`，且最近的 `game-state` 为 `BigMap focused=1`、
最近的 `overlay-visibility` 为 `map=1` 的记录。状态沿日志顺序跟踪，`app-init` 时清空；
场景沿接受的 `map-viewport-result` 跟踪。两秒采样是窗口统计，场景刚切换附近可能混入
上一窗口的少量绘制；这些记录不能用来计算帧级闪烁次数。

同次运行的场景切换发生在 05:18:58（接受 scene=6）及 05:19:30（接受 scene=1）。
回到大世界后源帧再次变旧。05:03 的 29 条记录中有 22 条源帧年龄 ≥500 ms，
`trackingMisses` 全为 0；持续报告 `state=BigMap observed=BigMap focused=1`，
这一分钟没有 `overlay-visibility` 翻转或 `map-ui-transition`。30 条状态记录全为
`BigMap focused=1`；152 次视口结果全部接受，内点比例中位数 0.93617，
已接受中心的 X / Y 跨度仅 0.375 / 0.44043 地图单位。地图视口基本静止且持续识别成功。

更直接的撤绘证据是同一分钟的 `map-context-suspended reason=render-unavailable`
**190 条**，`map-context-resumed reason=fresh-map` **191 条**。代码中
`DrawMarkerInteraction::Clear()` 的调用来自渲染循环的 `if (!drewMap)`，随后调用
`RoutePlanningService::MapUnavailable()`，从已观察地图变成不可用时才记录 suspended。
它与 UI 探针可见性不是同一条信号，证明这段窗口并非仅仅“统计帧率低”。
约 3.17 次 / 秒的撤绘循环还与源帧更新节奏非常接近；它支持源帧生命周期问题，
但 `render-unavailable` 没有细分门禁原因，仍不能单凭它确定哪个时效门被触发。
下层金库 05:19:00–05:19:24 也有 8 次 suspended、7 次 resumed 和 5 次
可见性变动，因此不能写成“下层金库绝对从未撤绘”，只能说显著少于上述大世界窗口。

重要读数限制：

- `attachedFps` 是成功图像附着的绘制迭代数，不等于非空标记数，也不等于闪烁次数。
- `markerDraws` 是 **小地图** 绘制统计，大地图窗口里为 0 不能解释成“大地图没画”。
- `trackingMisses` 仅统计进入附着调用后的失败；在 `Fresh`、显示上下文或
  `AllowsMap` 前被拒绝不会增加它。
- `trackMs` 是消息泵间一段工作的最大时间，包含绘制等工作，并非纯配准耗时。
  05:03 窗口的最大输入泵间隔均值约 177 ms，不能把它直接归因于 OpenCV。

定位仍持续成功。例如 `events-20261012.jsonl:76046`（05:02:53）为
`accepted=true scene=1 matches=47 inliers=44 inlierRatio=0.936170`。
它证明匹配能成功，**不证明最终标记帧已经及时生产并通过所有绘制门禁**。
异步定位的 `durationMs` 也不是生产标记帧的整段耗时。

## 代码链路与仍待区分的热点

1. `App::Start` 读取一帧后，在同一轮完成视口预测、接受结果的几何桥接与恢复提示、
   构建搜索候选、点位过滤、`PublishOverlayFrame`。源帧时间仍是原始捕获时间。
2. `PublishOverlayFrame` 的寿命为
   `max(500, 2 * max(updateMapDataCycleTime, updateMinMapDataCycleTime))` 毫秒。
   这批日志没有两个设置值，因此 500 ms 只能作为默认门槛的参考。
3. 渲染必须先通过源帧 `Fresh()`、显示上下文 / 客户区、
   `OverlayVisibilityFrame::AllowsMap()`，才能调用 `ImageAnchoredOverlay::Update`。
   当前捕获仍新鲜，不会自动延长源帧寿命；图像附着也不会绕过前面的门。
4. `OverlayVisibilityFrame` 采用捕获帧的 250 ms 时效。即使它的 `mapVisible`
   一直为真，若检测线程没有及时更新，`AllowsMap` 也会过期；旧日志不记录证据年龄。
5. 大世界可能较贵的具体路径包括视口预测 / 桥接、候选构建、整场景点位投影、
   完成状态查找与绘制。`DrawItemOnGameMap::GetAndFilterItemsData` 会逐组查询完成表，
   完成表查询会遍历记录；但附件没有玩家完成表及类别选择，不能据此宣判它是根因。
   另一个应检查的是源帧生产与渲染对共享完成表的锁竞争。

本地标签 `v2026.9.9.6` **已经包含** `frame->Fresh()`、`AllowsMap`、图像附着，
以及相同的源帧时效公式。9.9.6 到 9.18.2 改过捕获节拍、覆盖层呈现及帧工作；
本次没有同时采集这两个版本的原始帧 / 同配置日志，所以还不能把玩家的回归边界
归因到某一个提交。也没有证据足以认定帧生成、驱动或显卡是原因。
