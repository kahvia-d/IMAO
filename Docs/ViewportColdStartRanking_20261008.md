# 大地图冷启动：先用视觉索引排序，再决定搜什么

日期：2026-10-08
状态：已实现，本机测试通过，待实机验证
相关：`Docs/VisualIndexRebuildRegression_20261008.md` §9 第 4 项

## 一、起因：一个实机观察

玩家观察到，**冷启动时停在小地图界面，匹配速度往往比停在大地图界面更快**。

这个观察成立，而且不是错觉，原因是两条管线在"没有先验"这件事上的含义完全不同。

|  | 小地图界面 | 大地图界面 |
|---|---|---|
| 管线 | `GlobalVisualLocalizer` | `MapViewportLocalizer` |
| 查询图像 | `hud::kMinimap` = 184×177 | `hud::kMapCenterArea` = 1440×765（约 65 倍面积） |
| 尺度 | 已知（`Scene::MinimapScale`，默认 194/184） | 未知，玩家可缩放 |
| 候选怎么来 | 视觉索引倒排表排序，上限 `kMaximumCoarseCandidates = 12` | 对该场景**全部**瓦片建 FLANN，暴力 `knnMatch` |
| 冷启动时 | 只少一个提示，算法路径不变 | scope 落到 `Global`，即最贵的那一档 |
| 实测单次 | 中位 **4.8 ms** | 中位 **128 ms**、p90 352 ms、max 10.7 s |

数字来自 `measurements/accuracy-check/viewport_latency.py` 对既有日志的统计（记录在
`Docs/VisualIndexRebuildRegression_20261008.md` §10）。注意大地图那个中位数基本就是
`local-512` 的成本——571 次提交里 519 次是它，而且是接受率 91% 的正常路径。`Global`
远在这个之上，接受率只有 **13%**。

### 为什么冷启动把大地图顶到最贵的档位

`App.cpp` 提交时的 scope 选择：进入 `Local512` 需要 `prediction.confidence >= 2` 且
`sceneId` 已准入，或者 `activeWorldSearchPrior` 有效（要求 `playerLocationLock.valid`）。
冷启动两个都不成立，日志里就是那句
`scene-search-prior: used=false reason=no-confirmed-player-location`。

而 `prediction.sceneId` 本身只能来自一次绝对解算——**鸡生蛋**。

于是 `MapViewportLocalizer::Locate` 在 `Global` 下的代价是：

```
2 个裁剪区域（中央 350×350 + 整幅）
× 4 个缩放因子 { 1.0, 1.5, 2.0, 0.75 }   ← 非 Global 时只试 1.0
× 最多 9 个已准入场景
= 最坏 72 次 knnMatch，每次对手是该场景的全部瓦片
```

每次 `GetLocalMatcher` 首次都要复制 6–19 MB 候选并训练一个 FLANN 索引。所以冷启动的主要
成本不是 `knnMatch` 本身（0.1–0.4 ms），而是**为 9 个场景各建一次大匹配器**，其中 8 个注定
不是答案。

## 二、设计

一句话：**让大地图借小地图那套排序来选场景，但排序只能"缩小范围"，不能"下结论"。**

1. **检索预扫**（仅冷启动）。取这次请求本来就要用的"地图中央裁剪、原始尺度"图像，抽一次
   SURF 描述子，用视觉索引倒排表打分——和小地图的粗检索是同一段代码
   （`VisualIndexRetrieval::ScoreTiles`）。代价是几毫秒。
2. **按场景聚合**。每个场景取它自己得分最高的那块瓦片作为该场景分数（与小地图在单个网格
   单元内的 `max` 策略一致：同一地区的副本是重复观测，不是独立证据）。
3. **决定缩小到什么程度**：
   - 冠军领先亚军达到 `kRetrievalSceneLead = 1.5` 倍 → 只搜冠军这一个场景。
   - 两个场景咬得很近 → **两个都留**。两个坐标平面看起来一样，正是调用方已有的
     `acceptedScenes > 1` 歧义判定要处理的情况，让那个判定看见它们。
   - 排序为空 / 索引建不起来 / 某个场景算不出窗口 → 完全按原样，走全扫。
4. **每个保留的场景各带一份候选瓦片表，按排名取，不按半径圈**。一个候选集描述一个坐标平面，
   所以"保留两个场景"就需要两份。取法是照抄小地图的策略：**按得分从高到低往下拿，直到累计
   达到 `kRetrievalHintBytes = 20 MB` 或 `kRetrievalHintTiles = 64` 块**。
   **要么每个保留场景都有候选，要么一个都不用**：带候选的 plan 只比较一个尺度，留一个没候选的
   场景在里面，等于只让它在错误的尺度上被搜一次。
5. **三级阶梯**。冷启动构造最多**三个** plan：

   | 级 | 内容 | 代价 |
   |---|---|---|
   | 0 | 排序自己的最佳瓦片（20 MB / 64 块） | 一个十几 MB 的匹配器，**进得了缓存** |
   | 1 | **同一份排名，切宽 4 倍**（80 MB / 256 块） | 一次构建 |
   | 2 | 全扫（9 个整场景） | 565 MB、9 次构建、实测 11–23 秒 |

   第 1 级是第二场实机之后加的：排序对了但窗口没够到答案时，原来直接掉到第 2 级。而第 2 级是
   九次构建，第 1 级只要一次——形状和这条路径本来就在用的 `local-512 → local-1024` 阶梯一样。
   **没有第 2 级，一次排错就会丢掉一次本来能成功的定位**，所以全扫仍然是地板，排序只能比它更好。

其余请求（带先验的 `local-512`）只构造一个 plan，就是请求本身——**它们的路径一个字节都没变**，
也不为这个排序付出任何代价。

### 为什么按排名取，而不是按半径圈（第三版，2026-10-08 晚）

前两版都是"拿 top-12 块瓦片算一个中心+半径，再用半径圈出候选"，半径还会长大到把这些瓦片全
盖住（上限 2048）。第二场实机的构建记录判了它死刑：

```
local-matcher-builtMb92  Entries1     ← 冷启动的窗口
local-matcher-builtMb97  Entries1
local-matcher-builtMb98  Entries1
local-matcher-builtMb18  Entries2     ← 预热 local-512 的窗口
local-matcher-builtMb25  Entries2
```

`Entries1` 是"插进去之后缓存里只剩这一个"。缓存预算是 **48 MB**，一个 **92 MB 的条目永远
不可能和任何东西共存**——淘汰循环把它前面的全清空后就因为 `!localMatchers_.empty()` 短路而
退出，于是它照样被插进去，下一次构建再把它清掉。**结果就是冷启动的匹配器每次搜索都从头重建**，
而预热的 local-512（15–28 MB）能两个一起留住、反复复用。

所以候选改成按排名取：半径圈出来的那 92 块里有大量**排名根本没看上**的瓦片，只是恰好落在圈里；
排名往下拿则每一块都是查询真实描述过的地方。字节目标直接对齐"缓存留得住"这件事，而不是对齐
"覆盖得住"。半径那套常量（`kRetrievalHintMinRadius` / `kRetrievalHintMaxRadius`）随之删除。

### 为什么阈值是猜的，以及怎么不靠猜

`kRetrievalSceneLead = 1.5` 是一个**保守的估计**，不是量出来的。第一版里它决定了走"只搜一个
场景 + 瓦片窗口"还是"搜两个场景 + 全量瓦片"，所以它一旦猜偏，代价就是几秒。

实机日志会直接给出校准它需要的数据：每条 `map-viewport-result` 同时带
`scene=<最终接受的场景>` 和 `retrievalScene=<排序点名的场景>`，两下一比就是排序准确率。
字段清单见第四节的表。

**第一场实机（第三节）证明了这个阈值的危害，也正因为如此，第四节的改动把它降级成了一个
次要问题**：现在两条分支都会缩瓦片，阈值只决定"搜一个场景"还是"搜两个"，不再决定"缩不缩"。

## 三、第一场实机的数据（2026-10-08 15:56–16:03）

同一份日志，改动前后各一段。改变的只有程序，机器、地图、账号都没变。

| | 改动前（<15:53:48） | 改动后 |
|---|---|---|
| `scope=global` 结果数 | 16 | 8 |
| 接受 | 15（94%） | 8（100%） |
| 中位耗时 | **10,409 ms** | 780 ms |
| p90 / max | 10,735 / 12,195 ms | 7,783 ms |

**排序准确率 8/8**：`retrievalRanked=9` 每一次都是 9（九个已准入场景全部有分数），
`retrievalScene` 与最终接受的 `scene` **每一次都一致**。这是改前最没有把握的一点。

但耗时分布暴露了第一版的设计缺陷：

```
kept=1（有瓦片窗口）  n=2   626, 687 ms
kept=2（无瓦片窗口）  n=6   780, 7392, 7554, 7632, 7716, 7783 ms
```

`kept=2` 六次里五次是 7.4–7.8 秒。原因不是排序错了，是**排序对了却没缩小瓦片**：两个场景各自
用**全量**瓦片建匹配器，再乘上 2 个裁剪区域 × 4 个缩放因子 = 最多 16 次 `knnMatch`。

而这六次的 top/亚军比值是 **1.06、1.32、1.43、1.45、1.47** 和 1.32——全都**差一点点**够不到
1.5。也就是说 1.5 这条线恰好切在真实分布的正中间，把四分之三的搜索推到了慢分支上。
`retrievalRanked=9` 也说明排序本身是有区分度的，只是余量比预期小。

结论：**换掉"无瓦片窗口"这个分支，而不是去调阈值。** 每场景一个窗口之后，`kept=2` 也只是
两个几百块瓦片的小匹配器 + 4 次 `knnMatch`。

## 四、切区域时那 16 秒里，有一半是被丢掉的

同一个会话里切到另一个区域的过程（16:02:28–16:02:44）：

```
16:02:28  local-512   失败  matches=1   cropKeypoints=1016      252 ms
16:02:28  local-1024  失败  matches=6   cropKeypoints=3722      584 ms   ← 加宽这一档纯属浪费
16:02:28  global      提交  frame=868
16:02:36  bridge      accepted=0  inliers=0  requestFrame=868 currentFrame=1081
          ↑ 这一帧地图已经推进了 213 帧。搜索结果本身是**成功**的，但因为无法把它对齐到
            当前画面而被**丢弃**，而且此前**一行日志都不留**
16:02:36  global      重新提交  frame=1081
16:02:44  global      成功  7716 ms
```

两次 global 各约 7.5 秒，其中**一次白跑**。这不是两个问题，是**同一个**：搜索慢到跨了 200 多帧，
等它回来时玩家早就把地图移开了，桥接自然失败。搜索变快，这个问题自己就消失。

顺带补了一行日志：桥接失败时记 `accepted=false reason=bridge-rejected frameGap=<n>`。
不计成"接受"是因为外壳确实没有采用这个位置；但搜索的耗时是真实发生的，不该从延迟统计里消失。

**另外注意 `local-1024` 那一档**：两次切区域里它分别花了 584 ms 和 889 ms，都是 0 内点。
它设计上是为了"小范围平移"兜底，而切区域根本不在旧中心附近。本次没有动它——先看 global 变快
之后它在总延迟里占多大比例，再决定值不值得单独处理。

## 五、失败模式

| 情况 | 行为 |
|---|---|
| 排序点名了错误场景 | 该 plan 失败 → 同一次调用里继续跑全扫。多花一个小匹配器，不丢定位 |
| 排序把真实场景排到第 3 名及以后 | 同上，全扫兜住 |
| 某个保留场景的窗口没盖住真实位置 | 同上 |
| 某个保留场景算不出窗口 | 整个 plan 都不带窗口，两个场景都按全量搜、四个尺度都试（与改前一致） |
| 正确位置需要非 1.0 的缩放 | 带窗口的 plan 只比较 1.0；失败后全扫仍然试全部四个尺度 |
| 索引载不进来 / 词表形状不对 | `BuildVocabularyIndex` 返回空 → 不做预扫，行为与改前完全一致 |
| 查询描述子一个视觉词都没命中 | `ScoreTiles` 返回 false → 同上 |
| 索引有词表但没有 posting | 排序成功但全零分 → 视为"没排名"，同上 |

## 六、日志字段

`map-viewport-result`（接受、拒绝、以及新增的 `reason=bridge-rejected`）都带：

| 字段 | 含义 |
|---|---|
| `retrievalRanked` | 打分不为零的场景数。0 = 排序没点名（或这不是一次冷启动），走了全扫 |
| `retrievalScenes` | 排序保留的场景数（1 或 2） |
| `retrievalScene` | 排序点名第一的场景 |
| `retrievalRunnerUpScene` | 排序点名的亚军场景 |
| `retrievalTop` / `retrievalRunnerUp` | 冠军 / 亚军分数 |
| `retrievalTiles` | **冠军场景**的候选留下多少块瓦片。0 = 没有候选 |
| `retrievalMs` | 排序本身耗时 |
| `plansRun` | 这次请求实际跑了几个 plan（1 = 排序那个就成了，2 = 排序落空、全扫兜住） |
| `acceptedPlan` | 哪个 plan 答对的：**0 = 排序**，1 = 全扫，−1 = 都没成 |

新增字段都追加在行尾，且名字里不含 `scope=` 或 `durationMs=`，所以
`measurements/accuracy-check/viewport_latency.py` 的既有正则**无需修改**。

## 九、实机要看的

1. **`acceptedPlan` 的比例**。这是本轮最重要的一个数：`=0` 说明排序的候选就够、搜索一次成功；
   `=1` 说明排序落空、全扫兜住（那一次的耗时会是十几秒）。
2. **`retrievalTiles` 是否落在几十块量级**（对应 ~20 MB）。若普遍顶到 64 块的**块数**上限，
   说明这一带的瓦片很稀疏、20 MB 装得下几十上百块，那时"覆盖面"可能反而不够。
3. **`local-matcher-builtMbXX EntriesN` 里的 `Entries`**。窗口匹配器应当开始出现 `Entries2`
   （和预热 local-512 一样），而不是清一色的 `Entries1`。这是"缓存终于留得住"的直接证据。
4. `scope=global` 的中位与 p90 耗时。基线：改动前中位 10,409 ms；第一版中位 2,899 ms、
   p90 16,514 ms。
5. `retrievalScene` 与最终 `scene=` 是否仍然一致（排序准确率，此前 18/18）。
6. **`reason=bridge-rejected` 的频率**。它与搜索速度无关（1.4 秒那次也被丢了），是独立问题；
   本轮只是让它可见。
7. `local-512` 中位耗时有没有变（不应当受影响）。

## 十、不做什么

- **不动 `local-512` 的路径**。那是 91% 接受的正常路径，本次只碰冷启动。
- **不动 `local-1024` 那一档**。第四节末尾记了它在切区域时的浪费（584/889 ms，0 内点），
  但它设计上是为小范围平移兜底；先看 global 变快之后它占多大比例。
- **不缩小中央裁剪（394×425 → 184×184）**。这一条另有价值但代价在**正确性**一侧：描述子少
  3–4 倍会让排序变弱，小 patch 的仿射约束也弱得多，容易在大片海域/草原上自信地锁错位置。
  它必须作为**独立实验**做，不能和候选侧的改动混在一起测。
- **不把候选改成"逐块验证"**。小地图是逐块比（`kMaximumCoarseCandidates = 12`），但它的查询
  约等于半块瓦片、尺度已知；大地图的查询覆盖更多地形且尺度未知，逐块比会让几何估计失去
  上下文。按排名取一个**小集合**是同一思路的安全版本。
- **不让排序直接决定结果**。它永远只是一个 plan，后面跟着全扫。这条是设计的核心约束，
  不是实现细节。
- **不动 `GetLocalMatcher` 的缓存预算**（48 MB / 8 项）。它本来就已经挡不住全扫的 9 个场景，
  本次没有改它；窗口变小之后压力只会更低。
- **调 `kRetrievalSceneLead`**。第一场数据显示它切在真实分布正中间，但真正的问题不是这个数，
  而是它当时决定的那条分支没有窗口。现在两条分支都有窗口，样本更多之前不动它。

## 十一、第三轮：删掉 local-1024、补一级阶梯、加一项测量（2026-10-08 晚）

第二场实机（16:39–16:46）的结果是好的：global 中位 **2,899 → 381 ms**，排序 **17/18**，
其中 **15/18 由第 0 级直接答对**。但它暴露出三件事，这一轮各处理一件。

### 1. `local-1024` 那一档删掉了

同一场里 `local-1024` **提交 15 次、接受 1 次**，中位 501 ms、最慢 868 ms；而它要挡在前面的
`global` 中位 381 ms、18 次接受 14 次。**它比它想避免的那件事更慢，而且几乎从不成功** —— 因为
切区域之后它加宽的那个中心，正是刚刚失败的地方。

所以 `local-512` 失败现在直接进 `global`。随之删掉的还有 `MapViewportSearchScope::Local1024`，
以及只为它存在的 `lastMapViewportSearchCentre` / `lastMapViewportSearchSceneId`（加宽没了之后
它们成了只写不读的字段）。

### 2. 冷启动的兜底从两级变成三级（见第二节第 5 点）

18 次里有 3 次走全扫，11–23 秒：一次是排序点错了场景，两次是排序对了、但 20 MB 的候选没盖住
答案。新增的第 1 级把同一份排名切宽 4 倍 —— **一次构建，而不是九次**。

### 3. 加了"候选离答案有多远"的测量（只加测量，不动逻辑）

你点名的**黑海岸、泰缇斯之底**，它们的包特征点数是全场倒数：

| 包 | 场景 | 特征点 |
|---|---|---|
| timeriftruins | 8 | 2,072 |
| avinoleum | 4 | 12,634 |
| **tethys（泰缇斯之底）** | **2** | **13,329** |
| **blackshores（黑海岸）** | **1** | **15,168** |
| … | | |
| jinzhou（今州） | 1 | 220,090 |
| lahai（罗伊冰原） | 5 | 366,000 |

黑海岸的特征点只有罗伊冰原的 **1/24**。日志里黑海岸的 `local-512` 长期是
`matches=12–30 / inliers=12–27` —— **正好压在接受线（Strong 需要 ≥12 内点）上**，任何扰动都会
把它打掉。泰缇斯反过来：站住之后 `local-512` 是 `206/206` 很稳，**难在切进去**，而那一次恰好
是全场唯一一次排序出错（点名 Lahai，余量只有 1.09）。

但"候选到底够不够"当时**没有测量**，所以这一轮只加字段、不动逻辑：

| 字段 | 含义 |
|---|---|
| `candidateNearestM` | 最终接受的位置，离**第 0 级候选**最近的一块瓦片有多远 |
| `candidateReachM` | 最远的一块有多远 |

判读：如果第 2 级答对而 `candidateNearestM` **很大** ⟹ 是**覆盖不够**，第 0 级该取更多瓦片；
如果**很小** ⟹ **答案就在候选里面而匹配失败了**，那问题在尺度或匹配本身，加大候选没有用。

**下一轮先看这两个数，再决定稀疏地区要不要单独处理。**

## 十二、"准备"和"比对"到底各占多少（实测，2026-10-08 晚）

为了决定全扫该不该改成"一个区做完再下一个区"，给 `IMaoVisualRegression` 加了一个探针：

```
IMaoVisualRegression.exe --viewport-cost <repo-root> [sceneId]
```

它用**运行时真正的加载器**载入整棵资源树，然后按 `GetLocalMatcher` 的方式原样建匹配器并计时。
以下是 scene 1（World，含黑海岸）的结果：

```
scene 1 whole: tiles=3967
  prepare: copy=721 ms  train=8452 ms  total=9173 ms   keypoints=596694
scene 1 window: tiles=49
  prepare: copy=9 ms    train=60 ms    total=69 ms     keypoints=5037

  knnMatch query=1500   against whole:  49 ms   against window: 23 ms
  knnMatch query=3000   against whole:  97 ms   against window: 41 ms
  knnMatch query=6000   against whole: 202 ms   against window: 79 ms
```

| | 整个场景 | 20 MB 窗口 | 倍数 |
|---|---|---|---|
| **准备一次** | **9,173 ms** | **69 ms** | **133×** |
| 比对一次（3000 点） | 97 ms | 41 ms | 2.4× |

**准备比比对贵两个数量级。** 所以"来回跑仓库"的代价是：整个 World 场景要 **9.2 秒建一次**，而
全扫因为缓存只有 8 个位置要建它 **8 次**——**这就单独超过了观察到的 60 秒卡死**。日志里"每 10 秒
重建 9 个匹配器"也正好对上：那 10 秒里 9.2 秒是 World。

由此可以算出三种设计在最坏情况下的账：

| 设计 | 建几次 × 多贵 | 比对 | 合计 |
|---|---|---|---|
| 现状（整场景，区在内层） | 72 × 最高 9.2 s | 9–72 次 | **11 s（走运）～87 s（倒霉）** |
| 整场景 + 区提到外层 | 9 × 约 1.2 s 合计 | 72 次 | 约 **12 s**，且不再有长尾 |
| 窗口 + 区在内层 | 72 × 约 0.1–0.25 s | 72 次 | 约 **11–22 s** |
| **窗口 + 区提到外层** | **9 × 约 0.1 s** | 72 次 | 约 **5 s** |

也就是说：**把区提到外层（你说的"一本比完再比下一本"）不必多占内存，就能把最坏的 87 秒压到约 12 秒；
再让全扫也用窗口而不是整场景，能压到约 5 秒。**

### 另一个发现：20 MB 的预算其实只买到约 2.6 MB

探针里那一行 `window: tiles=49 ... keypoints=5037` 暴露了一件事。`TileBytes` 是按
`featureRowCount × 540` 估的，49 块瓦片估出 20 MB（≈38,800 个点），但去重之后**实际只有 5,037 个点**
——差了约 8 倍。

原因是 `featureRowCount` 数的是**行引用**，而瓦片是重叠的（384 大小、192 步长，World 又有 6 个包
互相重叠），同一个地图点被好几块瓦片引用。所以 `TileBytes` **系统性地高估了约 8 倍**，冷启动
第 0 级实际拿到的候选只有设计意图的八分之一——这正好解释了实机日志里 `retrievalTiles` 只有 5–17。

这一条要单独修：预算应该按**去重后的点数**算，或者干脆把目标调成"实际点数"而不是"引用数"。
现在它又快又小，是因为它比设计的小了 8 倍。

## 十三、修完之后的实测（2026-10-08 晚）

### 字节预算改成按去重点数算

上限拆成两级：第 0 级 `20 MB / 64 块`，第 1 级 `80 MB / 256 块`（都是四倍关系）。

```
20 MB 引用数（改前）       tiles=49   keypoints=5037   prepare= 69 ms
20 MB 真实点数，上限 64    tiles=64   keypoints=6012   prepare= 81 ms   ← 第 0 级
20 MB 真实点数，上限 256   tiles=256  keypoints=23611  prepare=343 ms
80 MB 真实点数，上限 256   tiles=256  keypoints=23611  prepare=347 ms   ← 第 1 级
```

第 0 级几乎没变（+12 ms），因为它的**块数上限先绑住**；真正的收益在于这个数现在**说的是实话**，
而且在瓦片互相重叠、排名前几名是重复瓦片的地区（实机里 `retrievalTiles` 只有 5–17 的那种），
它会自动继续往下取，直到拿到 20 MB 的**真实**点数。

### 全扫改成"每个场景用自己排名最高的那些瓦片"

理由就是第十二节那张表：准备一个整场景要 9.2 秒，准备一个窗口要 0.08 秒。实测九个场景的窗口：

```
scene 1: tiles=64 keypoints= 6012 prepare= 83 ms      scene 6: tiles=64 keypoints= 8111 prepare=116 ms
scene 2: tiles=64 keypoints=10635 prepare=147 ms      scene 7: tiles=64 keypoints=11361 prepare=171 ms
scene 3: tiles=64 keypoints= 3293 prepare= 45 ms      scene 8: tiles=27 keypoints= 2072 prepare= 29 ms
scene 4: tiles=64 keypoints= 6436 prepare= 90 ms      scene 9: tiles=64 keypoints=13933 prepare=199 ms
scene 5: tiles=64 keypoints= 5981 prepare= 85 ms
九个窗口合计：539 块瓦片，67,834 个点，常驻 34 MB，准备 966 ms
```

**34 MB 落在 48 MB 的缓存预算里，9 个条目也在 16 个的名额里——所以打转自己就没了。**
原本打算的"把场景循环提到外层"因此**不需要做**：打转的根因是"每次要建一个 9 秒的东西"，
不是"循环顺序"。循环顺序只是让这个 9 秒重复了八次。

顺带把缓存名额从 8 提到 16：名额本来是防"缓存变成地图的第二份拷贝"，而真正在防这件事的是
字节预算；但 8 比一次全扫要比的 9 个场景少一个，于是第九个一进来就把第一个挤掉。窗口只有 3 MB
左右之后，九个一起放进来绰绰有余，名额反倒是唯一还在让全扫打转的东西。

### 全扫仍然试全部四个缩放

窗口是按"正常缩放"那一张画面排出来的，但"画面被放大了"是排序看不见的一种失败，所以全扫
保留四个缩放。代价只是多几次比对（比对比准备便宜两个数量级），不多准备任何东西。

### 账

| | 改前 | 改后 |
|---|---|---|
| 全扫的准备 | 9 个整场景，World 一个 9.2 s，建 8 次 ≈ **75 s+** | **0.97 s** |
| 全扫的比对 | 9–72 次 | 9–72 次 ≈ 0.45–3.6 s |
| 全扫合计 | **11 s（走运）～ 80 s+（倒霉）** | **约 1.4 s（走运）～ 4.6 s（最坏）** |
| 缓存条目 | 全是 `Entries1` | 九个窗口同时reside（34 MB） |

这同时解释了实机里那个 60 秒卡死：**光 World 一个整场景被建 8 次就是 75 秒**，日志里"每 10 秒重建
9 个匹配器"里的 9.2 秒正是它。
