# 程序自更新

## 使用者操作

首次将 2026.9.9.4 或更高版本的完整程序 ZIP 解压到一个新的目录，打开 `IMao-Launcher.exe`。保留完整目录。原有 `IMao-WinUI.exe` 入口也会转交启动器，因此给它创建的快捷方式仍然可用。首次手动安装完成前，旧程序继续通过发行页升级。

设置 → 版本与地图资源 → 检查更新 → 下载新版程序。程序按分片发布：只有内容和本机正在运行的那一版不同的分片会被下载，其余分片直接从当前版本目录复制，不再重下整包。完成后点击“退出并更新”，或继续使用并在下次打开时启用。退出会等待地图工具、CoreHost 和正在保存的设置完成关闭。下载支持取消和重试；网络错误不会显示成“已经是最新版本”。

设置 →「下载源管理」选定程序更新的来源，二选一：**GitHub**（签名清单 + GitHub 分片；清单连不上时读 Gitee 的清单镜像）或 **Mirror酱**（检测与下载都走镜像，下载需要 CDK）。一个选择同时决定“谁回答有没有新版”和“谁搬字节”，不会从一个源检测、从另一个源下载：镜像的上传晚于签名清单，把镜像还没有的版本提示出来，只会让玩家点下去失败。镜像报告的版本与清单不一致时（镜像落后）不提供更新，界面写出镜像与清单各自的版本，并给出「改用 GitHub 下载源并检查」；镜像模式下没有 CDK 时检测照常、下载按钮禁用并说明原因。切换下载源会作废上一次检查结果，需要重新检查。

**地图资源（地区包）不受下载源影响**：它只在 GitHub Release 上发布，签名规则也不允许清单把下载指向 Gitee 或 Mirror酱，所以删掉某个区域之后的重新下载始终走 GitHub。走镜像更新程序时地图资源会跟着一起到——地区包的文件同时也在程序分片里。

启动成功后可选择“回退程序版本”，同样在退出后生效。地图资源的回退按钮独立工作；程序升级与回退仍会检查资源的基础版本与程序兼容范围。新类型地图仍需要程序支持，更新器不改变地区准入条件。

点位完成记录、路线、筛选与设置继续保存在原有 `%LOCALAPPDATA%\IMao-WinUI` 下。不要把用户数据复制进程序包。当前版本不做用户数据格式迁移。

## 安装布局与恢复

```text
安装目录/
  IMao-Launcher.exe               固定启动入口与内置公钥
  IMao-WinUI.exe                  首次手动安装的原始程序，亦转交启动器
  ...                            原始完整程序和基础资源，保留作最终恢复版本
  ProgramUpdates/
    state.json                   原子替换的当前、上一成功、待启用和试运行记录
    launcher.lock                每个安装目录只启动一个受管理实例
    running.lock                 子进程存活租约
    versions/<版本>-<包摘要>/
      update.json                原始签名封装
      app/                       此版本的完整程序，不混用旧 DLL
    staging/<事务标识>/           下载、解压和原生预检临时目录
      shards/<片名>.zip          本次要下载的程序分片，用完即删
```

运行中的程序文件从不覆盖或搬走。每次启动在执行安装版本之前重新验签、校验完整文件清单及构建来源，再记录试运行。候选 WinUI 窗口激活后，必须实际连接 CoreHost，确认资源就绪且两端快照 ID 一致，才能通过仅当前用户可访问的管道回报成功。启动器核对管道客户端 PID、随机会话值和程序版本，然后提交成功记录。

没有成功确认的试运行，在下一次启动恢复上一成功版本；启动器仍在运行时，候选崩溃或超时会立即尝试恢复旧版。不会反复尝试同一失败候选。状态文件损坏则停止自动选择，不猜测目录里的“最新版本”，保留文件供维护者排查。

启动器持有 Windows Job Object，WinUI 在创建 CoreHost 前加入该组。启动器崩溃或中断时，其 WinUI 和 CoreHost 子进程一起退出，避免旧核心继续运行。正常退出先完成应用关闭流程，再释放进程组。不同安装目录可各自运行；同一安装目录的第二个启动请求会提示已有实例。

本版保留原始程序、当前成功版本、上一成功版本，以及 `state.json` 里仍被引用的待启用与试运行候选。提交一次成功更新后，`ProgramUpdates/versions` 下不再被任何记录引用的目录会被清理——2026-10-09 实测过一个安装目录积到 8.60 GB，其中 6.17 GB 是四个没有任何记录引用的版本。原始程序在安装根目录、不在 `versions` 之下，因此永不被清理，它仍是最后回落的版本。清理是尽力而为的：残留目录被扫描器或尚未退出的子进程占用时留到下一次提交，绝不因此让启动失败；`versions` 或某个版本目录是符号链接/目录联接时一律不动。不要单独搬动 `ProgramUpdates/versions` 或删除更新状态。整体移动安装目录后，仍从根目录启动。程序自更新需要安装目录可写，沿用软件已有的管理员运行要求；只读目录需要重新解压完整包到可写位置。

**本次更新没有改动的文件与运行中的版本共享同一份字节**，不再逐字节复制一份：每个新版本只占它真正改动的部分（约 60 MB 自有产物 + 变化的资源），冻结的第三方库与 .NET 运行时只存一份。共享只发生在签名清单声明为逐字节相同的路径上，装配完成后整棵树仍按清单逐个文件校验，因此这种共享对校验、回退和原子发布都是不可见的——唯一能观察到它的是磁盘占用。写入版本目录的文件会被同时视为两个版本的内容，所以**不要把运行目录当作可写的配置位置**（窗口布局等用户设置一律写在 `%LOCALAPPDATA%`）。

**启动器与库街区桥接不随程序版本重建**，所以它们在版本之间同样是共享的。2026-10-10 之前它们把程序版本（与源码提交）印在自己的 PE 里，于是两个各 65 MB 的自包含单文件每版必变、每版都要重新落盘——内容其实没变。现在启动器带的是它自己的版本（`Version.props` 的 `IMaoLauncherVersion`，与启动器协议同时改），桥接与 Core 也各自有稳定版本，源码出处由包里的 `build-info.json` 与 `launcher-build-info.json` 记录。

稳定启动器本身不原地替换。启动器协议为 `1`，新清单要求更高协议或更换受信任发布密钥时，需要手动安装新的完整包。升级常规 WinUI、CoreHost、DLL 和基础资源无需手动替换文件。

## 签名及发布

清单 schema 保持 `1`，在 `app` 下添加可选 `package`，旧版客户端忽略新增字段并保留发行页入口。新增内容全部包含在现有 P-256/SHA-256 签名范围内：

| 字段 | 含义 |
| --- | --- |
| `launcherProtocol`、`architecture` | 所需启动器协议与 `win-x64` 平台 |
| `sourceCommit`、`baselineId` | 精确源码 SHA、基础资源标识 |
| `url`、`size`、`sha256` | 本仓库 Release 程序附件与完整 ZIP 校验；分片发布时指向 `IMao-v<版本>-shards.json` 描述符 |
| `files` | 每个文件的路径、大小和 SHA-256（整包与分片发布都以此为准） |
| `shards` | 可选：分片数组，每片有 `id`、`url`、`size`、`sha256` 与文件名清单（必须是 `files` 的不重不漏划分） |

程序包使用独立校验策略；地图包继续拒绝 EXE、DLL 和脚本。程序包拒绝路径穿越、重复与大小写冲突、链接、特殊文件、清单以外的文件、缺失文件及夹带用户数据。完整 ZIP 先校验大小和 SHA，再解压及逐文件验证，最后实际运行新版 CoreHost 的资源预检。分片发布时每个分片 zip 先校验自己的大小与 SHA，条目必须与它声明的文件清单完全一致（同样拒绝链接、重复、特殊文件与超长展开），组装完成后仍由同一套整树校验和原生预检把关。从本机当前版本复制的文件在复制过程中逐个核对 SHA-256，不符时该分片改走下载，因此本地损坏不会让更新失败，也不会被静默沿用。下载连接/响应超时和传输空闲超时沿用已有更新下载器。

`Build-ReleaseCandidate.ps1` 从同一干净源码构建独立自包含启动器、WinUI 和 CoreHost，并验证启动器版本及构建收据中的哈希。启动器使用 .NET 单文件自包含发布，随包提供，无需使用者安装 .NET。单文件运行时的本机库由 .NET 解压到其专用缓存目录。[.NET 单文件部署说明](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview)

正式 `UpdatePublisher prepare --program-release true` 有两种可选输入：`--program-zip <完整程序.zip>`（整包发布，工具检查真正的 ZIP 文件并把完整清单签入 `app.package`）或 `--program-shards true`（分片发布，工具直接按 `--app-root` 的路径规则切分、逐片打包，签名前先把所有分片重组回一棵树并跑完整校验）。两者都不能只提交一个未经签名绑定的下载地址。分片发布时 `Publish-ResourceUpdate.ps1` 会在创建草稿前逐个核对签名清单里每个分片与描述符的本地长度和 SHA-256，只上传指向本次 tag 的归档；未变分片保留它已发布的旧 URL 并进入公开可达性检查，`-ProgramZip` 与分片发布互斥。然后再走原有“验草稿附件 → 发布 → 公开下载验哈希 → 最后推进 stable”的顺序。

同一程序版本不能替换内容。仅资源发布必须使用 `--previous` 且不加 `--program-release`，完整保留已发布程序的签名包信息。客户端记录已接受清单序号和相同版本对应的内容摘要；主动本地回退走独立入口。候选程序清单只有在其程序版本高于当前运行版本、且该版本从未在本机准备过时，才能在渠道序号被重置后重新同步记录；其余过期或被改写的程序清单继续拒绝。

## 验证入口与边界

`scripts/Test-ProgramUpdates.ps1` 使用临时安装目录和独立测试密钥，包含实际子进程的启动确认、崩溃、超时、进程组回收、重启和回退。它已接入 `scripts/Test-Runtime.ps1`。生产启动器没有测试密钥参数，也不接受任意安装路径、外部公钥或启动命令。

端到端发行验收还应在独立目录使用完整程序包检查：首次 UAC、从设置页下载、正常关闭后重新打开、CoreHost 快照一致、主动程序回退以及原有用户记录。进程夹具和资源自检不能代替实际管理员 WinUI 或游戏内定位验证。
