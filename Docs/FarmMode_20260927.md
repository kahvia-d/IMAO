> "此外，我们设计一个机制来重置这个可刷新点位的完成情况。……当玩家下次开启刷怪采集模式的时候，
> 就查看这些数据的最近标记时间是不是已经隔天了……如果是隔天，就重置它们的完成清空（依旧要隔离收集物，避免影响到收集物）。"

## 二、定义

### 2.1 刷新类 = 采集物 ∪ 敌人（只有这两个大类）

分类来自库街区分类目录 `Assets/KuroMap/catalogs/catalog-<state>.json` 的**顶层分类名**。本地自带快照实测点数：

| 顶层分类 | 点数 | 是否刷新类 | 本次是否改动行为 |
|---|---|---|---|
| **采集物** | 10543 | ✅ | 自动勾 + 单独记账 + 每日清空 + 不进同步 |
| **敌人** | 7460 | ✅ | 同上 |
| 强敌 | 82 | ❌ | 完全不变 |
| BOSS | 42 | ❌ | 完全不变 |
| 挑战 | 63 | ❌ | 完全不变 |
| 收集物 | 3432 | ❌ | 完全不变（一次性，快速标记完成服务的就是它） |
| 探索 | 972 | ❌ | 完全不变 |
| NPC及服务点 | 59 | ❌ | 完全不变 |

**判据**：点位数据里**没有**刷新周期字段（`ItemDatas` 只有 `itemId` + `nameId` + `layer`，见 `Domain/MapData.h:16-23`；
上游 JSON 的 `online` 字段实测恒为 `false`）。所以只能拿 `nameId`（= `typeId`）反查顶层分类名。

**分类表的载体（实施时定案）**：**运行期从 `catalogs/catalog-*.json` 现推**，不生成新文件——
该目录本来就在地图资源包里、本来就由 `ResourceSnapshotContext` 校验，现推不会与上游漂移。
`IMao-Core/src/Runtime/RefreshableCategories.h` 读全部 `catalog-*.json`，取顶层名 `采集物` / `敌人` 的叶子 id 之并集。
**未知分类或缺文件时表为空 ⟹ 一切都不是刷新类**（功能静默不生效），而不是猜。
`scripts/Test-RefreshableCategories.ps1`（19 项）证明这个推导可作开关用，其中最关键的两条实测：
**名称表（`filter-items.json` + `new-state-filter-items.json`）里所有 采集物/敌人 id 都落在 catalog 的对应组里（漏判 = 0）**，
且点位数据用到的每一个分类 id 都能落到某个 catalog 组（未知 = 0）。实测点数：刷新类 **18574**，其它 5229。

**已知陷阱（已处理）**：声匣的 id 在分类目录里写作 `sx·qq` / `sx·lgn`，在点位数据里是 `sx_qq` / `sx_lgn`
（共 180 个点，见 `MapFilterCatalog.NormalizeOfficialId` 与 `scripts/Sync-KuroMapData.ps1`）。
两边共用同一份归一化（只重写 `sx` 前缀的中点）。⚠️ 目录里另有 10 个**非 `sx`** 的中点 id
（`qxzl·dlzw`、`sj·xzcy`、`xx·…` 等），它们**不属于**刷新类，两边拼写本来就一致，所以不改写是正确的。
⚠️ catalog 的 采集物/敌人 组比名称表**多 21 个 id**（我们没有对应点位的地区），多出来是安全的：判为刷新类也不会命中任何点。

### 2.2 每日纪元（epoch）

```
epoch = floor((本机本地时间 − 04:00) / 24 小时)
```

- 用**本机本地时间**的 04:00 作边界。玩家系统时区不是 UTC+8 时会和服务器差开，**本次不处理**。
- 不逐点记时间、不记次数（用户已删掉次数）。整个刷新类共用**一个**纪元。
- 反例说明为什么用纪元而不是"日期比"：今天 03:50 打的怪、今天 04:10 开模式——按日期不是隔天，但实际已经刷新了；
  按纪元边界判为过期，正确。

### 2.3 与既有设计约定冲突的地方（有意为之）

项目现有文档与代码反复声明"接近目标不会自动标记完成"：

- `IMao-Core/src/ImguiDraw/Items/DrawMarkerInteraction.cpp:633`
  `"实时规划已开启 · 接近目标不会自动标记完成"`
- `Docs/archive/AutoReplanCore_20260908.md:18`、`Docs/archive/AutomaticRoutePlanning_20260908.md:16`

## 三、行为规格

### 3.1 模式的开关

- **入口：路线工具栏**。⚠️ **这个项目里的"路线工具栏"指的是 WinUI 工具窗
  `IMao-WinUI/Views/MapToolsWindow.cs` 的 `RenderRoute`**（游戏内大地图上打开的那个「路径自动规划」面板，
  也是玩家截图看到的那个），以及桌面端的「路径自动规划」功能页 `FunctionPage.xaml`。
  按键 = `farm`，走 `MapToolsController` 的通用路线命令通道（`{action:"farm", enabled:!FarmMode}`）。
  **它不绑 `expectedSceneId/expectedGeneration`**——刷怪采集是路线自己的设置，不是当前地图视口的设置。
- ⚠️⚠️ **踩过的坑：原生 ImGui 那套路线工具栏是死代码。**
  `DrawMarkerInteraction.cpp` 里的 `BuildPlanningToolbar`（:601）只被 `PlanningPanel`（:691）调用，
  而 `PlanningPanel` 与 `DrawPlanningToolbar`（:705）**全项目没有任何调用点**；
  `DrawMapToolsLauncher`（:1191）在工具窗注册时直接 `return`，注释写着 *"The WinUI window is the only expanded UI."*。
  2026-09-27 我**只**改了那套死代码，于是实机上按钮根本不存在（用户连问两次"在哪"）。
  已在该函数上方留了注释说明改按钮要去哪；本轮把按钮加到了 `MapToolsWindow.RenderRoute`。
  **教训：加按钮之前先确认那个绘制函数真的被调用过（grep 调用点，而不是 grep 函数名）。**
- 键鼠与手柄都走现有工具栏导航（`RouteToolbarNavigation.h` 按屏幕几何选按钮、`RouteGamepadControls.h` 出
  `direction/activate`），**不新增任何手柄操作**。
- **开关记在路线自己身上（用户 2026-09-27 追加拍板）**：*"或许保存的路线可以记住开关？比如我这个路线保存了，
  就是专门刷怪的，那每次这条路线都开着收集刷怪开关。"* 于是 `Plan::farmMode` 随路线文件持久化：
  点开关时先写路线文件再动运行状态（写失败则开关不动），`activate` / `load` / 恢复活动路线时按路线里的值设置。
  **运行状态仍然随导航结束而关闭**（`stop` / 删除活动路线 / 换记录本），所以是"这条路线每次开始都是刷怪路线"，
  而不是"这个软件从此一直刷怪"。
  老路线文件没有这个字段 ⟹ **默认 false**（唯一安全的读法：默认开会在玩家没要求刷怪的路线上自动打勾）。
- **退出导航即自动关闭。**「退出导航」= **导航停止**，即 `r.active` 被丢掉的那两条路：
  点「退出导航」（`route:stop`）、删除当前活动路线导致导航停止（`route:delete`）；另外换记录本（`SyncProfileLocked`）也一并清掉运行状态
  （但接着会从恢复出来的路线文件里读回它自己的设置，见上一条）。
  **「暂停」（`route:pause`）不算**，模式保留。
  ⚠️ **「新建路线」（`route:new`）也不算**——它只是进入选点模式并**不**停止导航（`r.active` 保留），
  我最初把它当成"顶掉当前导航"是错的（`RoutePlanningService.cpp` 的 `action=="new"` 分支没有 `StopNavigationLocked`）。
  已用端到端用例钉住：进/出选点模式之后模式都还在。
- 关掉模式**不会撤销已经自动打上的勾**：那些记录留在账里，等 04:00 或玩家自己取消。

### 3.2 自动勾的触发条件（全部满足才勾）

1. 刷怪采集模式开着，且正在导航（`navigationStatus` ∈ {`navigating`, `waitingForLocation`}；暂停/结束/未开始都不算）。
2. 沿用现有 `ProximityObservation` 的**全部有效性门禁**（`App::PublishPresentedOverlay`，`App.cpp:2572-2594`；
   `ProximityValidLocked`，`RoutePlanningService.cpp:241-248`）：小地图可见、定位可靠、游戏在前台、叠加层允许、
   档案/路线/`orderRevision`/目标 key/会话都对得上、位置与呈现都在有效期内。
3. 目标是**当前这条活动路线上的**点，且序号 **≥ 当前目标**（当前目标本身 + 后续目标）。**不在路线上的点位一律不勾。**
4. 该目标类别是**采集物或敌人**（收集物只能手动勾）。
5. 该目标尚未完成；**被跳过的目标不勾**。
6. 玩家到它的距离 < 设定范围，并且**持续约 500 ms**（沿用 `NearbyConfirmation` 的连续帧确认写法，
   `AutoReplanPolicy.h:67-84`；一帧不算数）。

**打勾范围** = 当前导航目标 + 后续目标里也在范围内的那些（用户第 4 条原话）。

### 3.3 范围设置

- 单位：**像素**（沿用现有两个范围的口径）。默认 **30**，可调 **5–120**。
- 位置：WinUI 设置页「操作优化」卡片，与「完成点位触发范围 · 像素」（:`165`）、「查看攻略触发范围 · 像素」（`:166`）并排。
- 会**落盘**，并走 `configure` 下发给核心（见 §5.3）。
- ⚠️ 已知：同一像素数在不同分辨率/缩放下代表的实际距离不同（`pixelsPerMapUnit = 小地图裁切宽 / 184 / 1.0543`）。
  用户明确接受："沿用像素，由玩家自己适应"。

### 3.4 反馈

用户要求：*"给反馈：收集刷怪模式自动标记xx个。"*

- 每次自动勾产生一批（1 个或多个）后，在路线工具栏的 notice 行显示：
  **「刷怪采集模式自动标记 N 个」**。
- 该行是既有的瞬态文案位（`ToolbarUi.notice`），会被后续文案自然顶掉，不需要新的提示通道。
- 不做撤销入口（用户未要求；且这批勾本来就是"到了就算做完"的语义）。

## 四、数据

### 4.1 文件

新增一本**独立账本**，放在与主记录本同一目录：

```
%LOCALAPPDATA%\IMao-WinUI\SavedPoints\profiles\<profileId>.farm.json
（主记录本是同目录的 <profileId>.json）
```

结构（建议）：

```json
{
  "schemaVersion": 1,
  "profileId": "local",
  "epoch": 20693,
  "points": { "8:1469330615266230272": true }
}
```

- 键 = `"<stateId>:<pointId>"`，与 `AutoRoute::Key` / `MarkerCompletionStore` 的点位身份一致。
- `epoch` 是 §2.2 的整数。
- **读或写时**发现 `epoch` != 当前纪元 ⟹ **整本清空**，写上新纪元。
  - 这是"重置"的全部实现。不区分自动勾与手动勾（用户第 2 条：效果一样）。
- 每帧不做时区转换：本地 04:00 偏移缓存，帧内只做一次整数比较。

### 4.2 读取漏斗（只有两处）

主记录本的完成状态全项目只有一个读入口：

- `DrawItemBase::IsPointCompleted(scene, item)`（`DrawItemBase.cpp:326-328`）⟹ 调用点遍布
  `DrawMarkerInteraction` / `DrawItemOnMinMap` / `App.cpp` / `RoutePlanningService` / `CoreHostMain`。
- `DrawItemBase::GetFilteredPoints(scene, nameId)` → `MarkerCompletionStore::CompletedIds`（`DrawItemBase.cpp:322-324`），
  筛选页用。

**这两处各合并一次 farm 账本即可**，其余调用点自动生效。

### 4.3 一次性迁移（必须做）

主记录本（`profiles/<id>.json`）里现存/将来可能出现的**采集物 ∪ 敌人**记录必须搬进新账本，否则：

- 它们仍然带着 `pending=true`，而这两类**不再上传** ⟹ 同步页永远显示一笔还不掉的"待上传"。

迁移规则：

1. 遍历主记录本 `points`，对类别 ∈ 刷新类的记录：`completed=true` 且**属于当前纪元**的搬进新账（`true`），
   然后从主记录本删除该记录（连同 `pending` / `remoteCompleted` / `acknowledgedRevision` 等同步簿记）。
2. 主记录本里**其它 6 个分类的记录一字不动**。
3. 迁移是幂等的：搬过的记录不会再出现。

同一条分类规则还要用在另外两处**导入路径**，否则旧记录会把刷新类塞回主账本：

- `MarkerCompletionStore::Load` 里对 `SavedPoints/account_1.json` 的自动导入（`MarkerCompletionStore.h:480-499`）；
- `markerImportLegacyProgress` 命令（`MarkerCompletionStore.h:92-127`）。

## 五、同步

### 5.1 不上传 —— 靠"不在主记录本里"天然成立

自动勾写入 farm 账本，**不进主记录本**，因此 `markerGetOutbox` 永远看不到它们。
需要动的四条上传通路**一条都不用改**：

| 通路 | 位置 | 为什么不用改 |
|---|---|---|
| 定时出箱上传 | `KuroProgressSyncService.PushPendingAsync` | 出箱来源是主记录本 |
| 标记后立即推送 | `markerCompletionChanged` → `KuroLocalChange.TryRead` → `KuroAutoSyncService` | 见 §5.4：自动勾发**另一个**事件类型 |
| 应用远端 | `markerApplyRemote` | 主记录本里没有这两类的记录 |
| 初始化基线 | `markerInitializeSync` | 同上 |

> 反面教材（**不要这么做**）：把自动勾写进主记录本、再在上传时过滤。`markerApplyRemote` 会对该区域
> **所有**点重算 `const bool pending = desired != remote;`（`MarkerCompletionStore.h:323`），
> 下一次同步就会亲手把它重新排进上传队列。

### 5.2 不下载 —— ⚠️ **初稿在这里推断错了，实测推翻**

初稿写的是"`markerApplyRemote` 只会为 `command.points` 里**显式提供**的身份调 `FindOrCreate`，
而桌面端只发 `remoteIds`，所以远端下发不会造出刷新类的记录"。

**这是错的。** `DrawItemBase::HandleMarkerCommand` 在收到 `markerPreviewSync` / `markerApplyRemote` /
`markerInitializeSync` 而调用方**没给** `points` 时，会**自己把该 state 下全部本地点位身份**填进 `points`
（`markerIdentities` 是 `Iniți()` 里按全部分类（含采集物/敌人）建的全量索引）。于是：

- `markerApplyRemote` 会对 `remoteIds` 里的每个 id 调 `FindOrCreate` ⟹ **云上只要有一个采集物/敌人 id，
  它就会被写回主记录本、变成"已完成"**，第二天日重置立刻被撤销；
- 而且它还会被报告成 `unmappedIds`，同步页永远显示"N 个点位对不上本地目录"。

**所以 §5.3 的过滤是"承重"的，不是装饰。** 结论本身不变（这两类不下载），但理由和实施位置都改了。

### 5.3 需要动同步的一处（实施位置：原生核心，不是桌面端）

- **位置**：`DrawItemBase::HandleMarkerCommand`，在把命令交给 `MarkerCompletionStore::Execute` **之前**，
  对 `markerPreviewSync` / `markerApplyRemote` / `markerInitializeSync` 的 `remoteIds` 逐个丢弃刷新类 id。
- **为什么放原生而不是 `KuroProgressSyncService`**：这里是**所有**调用方（桌面端、测试、将来的其它调用者）
  的必经之路，放一处就全覆盖；放桌面端则要求托管侧另有一份分类表，而且漏掉任何一个调用方就会重现上面那条 bug。
- 拒绝的是"云上这两类的完成在 IMAO 里彻底看不见"，符合用户"这两大类都不上传库街区了，还管云端做什么呢？"。

### 5.4 自动勾的事件类型

- **不要**复用 `markerCompletionChanged`（`KuroLocalChange.TryRead` 会认它，`KuroAutoSyncService` 会立刻上传）。
- 发一个独立事件（如 `markerFarmCompletionChanged`），携带 `profileId` / `stateId` / `pointId` / `nameId` / 批次数量。
  外壳侧只用它显示 §3.4 的反馈，不做任何上传。

### 重置到底什么时候被检查（回答用户提问）

**不是定时器。判据是"读或写 farm 账本时顺手比一次整数"**：`FarmCompletionStore` 的每个公开方法
（`Completed` / `CompletedIds` / `Set` / `SetMany` / `Absorb` / `Epoch` / `Expired` / `TakeExpired` / `Size` /
`SelectProfile`）开头都调 `ExpireLocked()`，它算一次 `floor((本机时间 − 04:00)/24h)` 与账本里的 `epoch` 比，
不等就整本清空并把新纪元写回。

实际触发点因此是"任何一次读"：

| 触发 | 时机 |
|---|---|
| 画大地图/小地图时为每个采集物·敌人点位问"完成了吗"（`IsPointCompleted`） | **叠加层在画 → 04:00 后第一帧（几十毫秒内）** |
| 路线刷新"剩余目标"（`RefreshCompletedLocked` → `CompletedNow`） | 任何路线/标记变化时 |
| 打开筛选页的"已收集"（`GetFilteredPoints` → `CompletedIds`） | 玩家打开该页时 |
| **任何写入之前**（`SetMany` 先 `ExpireLocked`） | 04:01 打的第一只怪不会记进昨天的账 |
| 启动建账本（构造函数 → `LoadLocked`） | 每次启动 |

边界情况：
- **IMAO 没启动 ⟹ 什么都不发生**（没有后台服务/计划任务）。文件停在旧纪元，下次启动第一次读才清，
  所以不存在"过期的勾还留在界面上"的窗口。
- **04:00 整正在导航**：按用户拍板不做特殊处理——下一帧就清空，路线退回第一个目标（现在还会调
  `OnMarkerChanged`，所以退得干净）。
- **用本机系统时间**（不是服务器时间）：系统时区非 UTC+8 或时钟不准就会错点。已知限制。
- **磁盘写失败不会让重置失效**：内存里已清空，只是没落盘；下次读会再推一次（`ExpireLocked` 里的写包在 try 里）。
