# 视觉索引重建：为什么重建后反而变差（2026-10-08）

## 一、结论先说

**重建视觉索引的路径存在回归，已回退。** 现在发布状态用的是**重建前的索引**，
它与迁移后的 v2 特征验证兼容（14/14 合并成功、词汇表统一）。

- 重建版索引（15 个，15 个索引）**不是坏的**——它能通过运行时全部加载校验
- 但装上之后**小地图识别质量崩塌**：同一区域、同一台机器、同一份 v2 特征，
  `inliers` 从 18 掉到 **0**，`quality` 从 `Strong` 掉到 `Marginal`
- 换回重建前索引**立即恢复**（`Strong` 占比 42–44%，与迁移前一致）

## 二、事情的起因

`Assets/FeaturesDatas/KuroTilePacks` 于 2026-10-08 完成 v1→v2 就地迁移
（描述子 uint8 量化 + 载荷 deflate，882 MB → 120 MB，见 `Docs/FeatureSizeComparison-*`）。
迁移只改了**磁盘表示**，内存里的描述子取值基本不变。

发版前考虑"一步到位"，即**用 v2 数据重建全部视觉索引**，理由是：

1. 索引当时停留在 2026-09-23/09-30，是 v1 时期构建的
2. 索引体积（112.2 MB）已经**超过特征二进制本身**（102.5 MB）
3. 希望"索引与特征配套"这件事在记录上是干净的

## 三、为什么"必须整体重建、且必须复用词汇表"

这是重建方案的技术前提，值得单独记下来：

**词汇表不可复现。** `MapVisualIndexBuilder::Build` 的聚类是确定性的
（`cvflann::seed_random(0x494d414fU)`，固定采样 `min(rows, 65536)`，
固定 `KMeansIndexParams(16, 11, FLANN_CENTERS_GONZALES, 0.2f)`），
**但它对输入敏感**：用 v2 数据重新聚类得到 `3723e22a…`，
而线上 14 个分片共用的那套是 `8bd80ebd…`。

实测：全部 14 个包的迁移偏差都**恰好顶在半个量化步长**（`0.500 of a step`，
最坏 0.003006）。就是这个量级的位移改变了 k-means 的簇边界。

推论：**任何重建都必须一次覆盖全部 15 个索引（14 个分片 + 基础索引），
并且必须复用同一套词汇表**，否则新旧词汇表混用 → 合并失败 →
运行时**静默降级**（`visualIndexReady=false`，不报错、只是粗检索失效）。
这是最危险的失败模式，因此后来加了 `scripts/VisualIndexVocabulary.ps1` 断言。

## 四、A/B 实测（决定性证据）

| 时间 | 索引 | 同一区域（scene 3 隐海试验场）的追踪 |
|---|---|---|
| 12:36 | **重建版** | `quality=Marginal inliers=0 ratio=0.000`（67 条，内点全 0） |
| 12:44 | **重建前版** | `quality=Strong inliers=18 ratio=0.667`（357 条，正常） |

两次测试之间**只有索引变了**：同样的 v2 特征、同样的宿主、同一台机器、同一区域。

用户的主观描述与此吻合：「在无法识别的区域跑出去很远很远才识别到」——
机制是**索引选错候选 → 该位置匹配不上（内点 0）→ 一直重试 → 直到跑到能匹配上的地方**。

## 五、差异缩到最小范围（`measurements/tile_table_diff.py`、`index_diff.py`）

对比重建前 / 重建后的隐海试验场索引：

```
vocabulary    2097152  相同        ← 词汇表没变
featureRow    7836344  相同        ← 每个关键点的词分配没变
瓦片键/边界框  581 个   全部相同     ← 瓦片几何没变
histogram     4238592 → 4242528   ← 唯一变了的东西（581/581 瓦片）
posting       6357888 → 6363792
```

**只有 TF-IDF 直方图权重变了。** 权重 = `tf * idf`，其中：

- `tf = count / coreFeatureCount`（词频）——没变
- `idf = log((documentCount+1) / (documentFrequency[word]+1)) + 1`——**变了**

而 `documentFrequency`（某词出现在多少瓦片里）由词分配决定，词分配没变。
所以差异只能来自**特征点坐标**：

> 旧索引是用**迁移前的 v1 特征**构建的；重建时用的是 **v2 特征**。
> 量化把每个坐标移动了最多半个步长，**少数恰好压在瓦片边界上的点翻到了相邻瓦片**，
> `documentFrequency` 因此改变，于是**所有瓦片的归一化权重**都跟着偏了。

这解释了一个乍看矛盾的现象：条目只差 **66 / 64557（0.1%）**，却让**每一片**的权重都偏了——
而粗检索正是拿查询直方图与这些权重算余弦相似度（日志里 `retrievalScore` 只有 0.06–0.11）。

## 六、被排除的怀疑

| 怀疑 | 结论 | 依据 |
|---|---|---|
| 体积压缩（v2 量化）导致 | **否** | v2 只改磁盘表示；关键点逐位相同，描述子偏差有界且已量化验证 |
| 索引被运行时拒绝 | **否** | `IMaoVisualIndexProbe` 按运行时加载路径验证，**两个版本都通过**全部不变量 |
| 词汇表混装 | **否** | 14 个索引 `vocabularySha256` 全部相同（`8bd80ebd…`） |
| 索引加载失败 | **否** | 日志 `visualIndexReady=1`、`error=`（空），14 个包 124 ms 内加载完成 |
| 大地图升级逻辑 | **否**（对小地图） | 该改动只在 `map-viewport` 路径；小地图走执行器路径 |

## 七、当前状态与回退方式

- **发布状态**：仓库与运行树均使用**重建前的 14 个索引**
- 重建版索引（15 个，含基础索引）：`measurements/index-backup/rebuilt-current/`
  （该目录被 gitignore，不在版本库里）
- 两者**词汇表相同、瓦片几何相同**，所以可互相替换且都能与 v2 特征合并
- 验证：14/14 合并成功、发布门禁 14/14、词汇表断言通过

## 九、遗留问题（下次讨论的起点）

1. **根因验证未完成**：上面第五节是"由排除法推出的最可能解释"，**没有直接证实**。
   最干净的验证是**用 v1 特征重建一次**（需要先把 v1 特征从 git 历史/LFS 恢复出来），
   如果得到工作正常的索引，则"量化是唯一变量"成立。
2. **或者**：直接查清 `documentFrequency` 差异是否真的足以造成内点归零。
   0.1% 的权重变化 → 匹配完全失败，这个跨度**大得可疑**，
   有可能还有第二个未发现的因素（例如 `posting` 增量的排序/偏移影响粗检索）。
3. **索引体积仍是最大的一块**（112.2 MB > 特征 102.5 MB）。
   若要继续压体积，下一块该动索引；但那属于独立议题，且必须走"全部一起重建"的路。
4. **大地图切区域后识别慢（10–20 秒）** 与**冷启动在大地图很慢**是另外两个问题，
   与本次索引回退无关：前者已有一处修复（升级窗口围绕"刚失败的中心"扩，而非会话起始中心），
   后者需要让大地图用自身预测引导首次搜索（尚未做）。
